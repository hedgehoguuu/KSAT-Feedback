# KSAT-Feedback

한 사이트에 세 가지가 들어 있다.

1. **무료 시험지 피드백 접수** (`/`) — 9모 시험지 사진을 받아 튜터가 보고 메일로 회신한다.
   스펙은 `../PRD_9모_시험지_피드백.md` (v1.0).
2. **유료 관찰반 모집** (`/class`) — 그 피드백을 받은 학생에게 3인 팀수업을 알리고 신청을 받는다.
   설계는 `docs/class-landing-prd.html` (PRD v1.1).
3. **성적 관리** (`/lms`) — 수업이 시작된 반의 **수학(미적분) 실전 모의고사**. 정답표 · 채점 ·
   누적 성적, 그리고 시험 뒤에 학생이 올린 질문에 튜터가 답을 달아 **답변 PDF** 로 보낸다.
   아래 「성적 관리」. 2026-09-17 에 국어에서 수학으로 바꿨다.

접수는 2026-09-02 에 열었다.

## 돌려보기

```bash
npm install
npm run dev            # http://localhost:3000
```

Supabase 키가 없어도 ②단계까지 전부 동작한다. 환경변수가 비어 있으면 업로드가 **mock 모드**로 떨어져
서명 URL 발급·업로드를 흉내낸다. 파일 이름에 `fail` 이 들어가면 일부러 실패시켜서 FE-4 실패 UI를 볼 수 있다.

실제 스토리지에 붙이려면 `.env.example` 을 `.env.local` 로 복사하고 값을 채운 뒤,
`supabase/migrations/` 의 SQL 을 **번호 순서대로** Supabase SQL Editor 에 붙여넣고 실행한다.
전부 여러 번 돌려도 안전하게 적혀 있다. 무엇이 빠졌는지는 `/setup` 이 알려준다.

## 배포

Vercel 이 `main` 에 푸시될 때마다 자동 배포한다. 사람이 할 일은 두 가지뿐이다.

**환경변수** (Vercel → Settings → Environment Variables)

| 이름 | 없으면 |
|---|---|
| `SUPABASE_URL` · `SUPABASE_SERVICE_ROLE_KEY` | mock 모드로 떨어진다. 접수도 반 목록도 저장이 안 된다 |
| `ADMIN_PASSWORD` | `/admin` 이 아예 안 열린다 (열어 두지 않는다) |
| `WORKER_SECRET` | 운영용 주소가 전부 잠긴다 — 막힌 접수를 되살릴 수 없다 |
| `CRON_SECRET` | 매일 자동 정리가 안 돈다 (`WORKER_SECRET` 과 같은 값을 넣는다) |
| `GMAIL_USER` · `GMAIL_APP_PASSWORD` | 접수 확인 메일 · 신청 알림 메일 · **답변 PDF 메일**이 안 나간다 (PDF 는 학생 화면에서 받는다) |
| `LMS_SESSION_SECRET` | 성적 관리 로그인 서명에 `ADMIN_PASSWORD` 를 대신 쓴다. 둘 다 없으면 `/lms` 가 안 열린다 |
| `ANTHROPIC_API_KEY` | 정답표 사진 읽기와 **학생 시험지 자동 채점**이 꺼진다 (손으로 매기는 것은 그대로) |
| `NOTION_TOKEN` · `NOTION_DATABASE_ID` | 접수가 Notion 에 안 올라간다 |
| `SITE_URL` | 선택. 직접 산 도메인을 붙였을 때만 넣는다 (없으면 vercel.app 주소를 쓴다) |

`SUPABASE_SERVICE_ROLE_KEY` 에 **절대 `NEXT_PUBLIC_` 을 붙이지 말 것** — 붙이면 브라우저로
새어 나가 DB 전체가 열린다.

**SQL** — `supabase/migrations/` 를 번호 순서대로 한 번씩 실행한다. 전부 여러 번 돌려도 안전하다.
**`0015_lms_math.sql` 은 코드를 올리기 전에 돌린다** — 수학용 코드는 국어 모양의 표를 읽지 못하고,
옛 코드는 수학 모양의 표를 읽지 못한다. 둘 사이의 몇 분 동안은 `/lms` 가 오류를 낸다.
**`0016_lms_photo_grading.sql` 도 코드를 올리기 전에 돈다** — 새 코드는 응시의 `answers_source` 칸을 읽는다.
0016 은 지금 돌고 있는 코드(0015)와도 맞아서, 먼저 돌려 두면 끊기는 시간이 없다.
**`0017_lms_grading_guard.sql` · `0018_state_guards.sql` 도 코드를 올리기 전에 돈다** — 오래된 채점 화면을 내용으로 알아보는 판과
정답표 저장의 잠금 순서가 여기 있다. 0016 을 언제 돌렸든 0017 하나로 맞춰진다. 안 돌렸으면 `/setup` 의
'0017 이후 SQL' 이 빨간불이다.
**`0019_apply_outcome.sql` 도 코드를 올리기 전에 돈다** — 새 코드는 신청 id 를 미리 뽑아 넘기고, 돌려받은 id 가
같을 때만 알림을 보낸다. 0019 없이 새 코드가 돌면 옛 함수가 넘긴 id 를 무시해서 새 신청도 알림이 안 간다.
0019 는 지금 돌고 있는 코드(id 를 안 넘긴다)와도 맞는다.

**이미 돌린 마이그레이션 파일은 고치지 않는다.** 고칠 것이 생기면 새 번호로 낸다. 0017 부터 파일마다 끝에서
`schema_migrations` 에 제 이름을 적고, `/setup` 이 `lib/health.ts` 의 `REQUIRED_MIGRATIONS` 와 견줘 빠진 파일을
짚는다 — 함수가 '있는지' 만 봐서는 옛 판인지 새 판인지 모른다. 새 마이그레이션을 더하면 그 목록에도 한 줄 더한다.

### 배포하고 나서 열어볼 것

1. `/setup` — 빨간불이 없는지. 무엇이 빠졌고 어떤 SQL 을 돌려야 하는지 여기가 말해 준다.
2. `/class` — 반이 보이는지. "불러오지 못했어요" 가 뜨면 DB 쪽 문제고, "열린 반이 없어요" 는
   정말 `open` 인 반이 없다는 뜻이다. 둘은 다른 말이다.
3. `/admin` — 로그인되고 반이 보이는지.
4. `/lms` — 튜터로 들어가 회차를 열고 정답표 · 채점 · 답 달기 화면이 뜨는지. `/setup` 의
   '수학 수업 표' · '시험지 사진 · 답변 PDF 저장소' · '사진 자동 채점 표' 가 초록불이어야 한다.
   '사진 읽기' 가 빨간불이면 `ANTHROPIC_API_KEY` 가 없어 자동 채점만 꺼진 것이다.
5. `/robots.txt` — `Sitemap:` 줄이 있는지. 없으면 빌드할 때 도메인 환경변수가 없었다는 뜻이다.

## 운영자용 화면

- `/setup` — 무엇이 준비됐고 무엇이 빠졌는지 ✓/✗ 로 보여준다. 배포 후 여기부터 열어볼 것.
  SQL 을 안 돌렸으면 그 항목이 빨갛게 뜨고 어떤 파일을 실행해야 하는지 알려준다.
- `/admin` — 개설 클래스와 신청자. 반 이름·시간·튜터·학력·증빙·수강료·정원·상태를 여기서 고친다.
  **배포 없이 즉시 반영**된다. `ADMIN_PASSWORD` 환경변수 하나로 잠기고, 같은 잠금이 `/setup` 에도 걸린다.
- Supabase Table Editor > `app_settings` 한 줄 — 접수 on/off, 상한, 과목별 off, 마감 문구. **배포 없이 즉시 반영**된다.

문항 번호는 번호만 받지 않고 **번호와 그 이유를 한 쌍으로**, 줄을 추가해 여러 개 받는다(`items` 타입).
답변 값이 문자열만이 아니라 `{ no, why }` 목록도 될 수 있는 이유다.

**국어만 문항이 다르다 (2026-08-30).** 국어는 영역·지문별로 물어볼 것이 달라 공통 문항으로는
필요한 정보가 안 나온다. `CONCERN_QUESTIONS_BY_SUBJECT.korean` 에 여덟 문항이 따로 있고,
나머지 과목은 공통 다섯 문항 그대로다. 보기에서 고르는 `choice` 타입은 여기서 처음 쓰는데,
**같은 보기를 다시 누르면 선택이 풀린다** — 전부 선택 입력인데 한번 누르면 못 되돌리면 곤란해서다.

국어의 문항 번호 예시는 "3페이지 독서지문, 7번" 이라 번호 칸이 숫자만 받으면 안 된다.
숫자 자판 강제를 풀고 칸도 내용에 맞게 늘어나게 두었다.

**원점수는 전 과목 공통**이고 고민 문항이 아니라 별도 칸이다(`submission_subjects.raw_score`).
등급이 아니라 원점수인 이유는 튜터가 시험지를 볼 때 몇 점짜리를 틀렸는지 맞춰봐야 하기 때문이다.
선택 입력이라 채점 전에도 접수할 수 있다. 만점은 과목마다 다르므로(국·수·영 100,
통합과학·통합사회 50) `subjects.ts` 에 두고 화면 안내와 서버 검사가 같은 값을 본다.

운영 쪽 미결: Q8(접수 확인 메일 발송 주체·발신 주소), Q9(Notion DB 를 팀 워크스페이스에 둘지 분리할지).

## 모집 페이지 (/class)

9모 시험지 피드백을 받은 학생에게 유료 수업을 알리는 화면이다. 설계는
`docs/class-landing-prd.html`, 수업 자체의 정의는 `docs/class-180.html` 에 있다.

페이지는 세 덩어리다. **수업 구조**(180분을 80:10:90 으로 쓰는 자와 실제 관찰 기록 네 줄) →
**받는 학생 / 받지 않는 학생** → **지금 열려 있는 반**. 앞의 둘은 코드에 박아 두고,
마지막 하나만 DB 에서 읽는다. 바뀌지 않는 것을 편집 가능하게 만드는 것이 관리 비용이다.

- **읽기** — `/class` 는 서버 컴포넌트가 `supabaseAdmin()` 으로 읽어 그린다(`force-dynamic`).
  `classes` 에는 익명 정책을 만들지 않았다. 브라우저는 Supabase 에 직접 붙지 않는다.
- **신청** — 학생이 채우는 칸은 넷뿐이다: 이름 · 9모 접수번호 · 학부모 연락처 · 동의.
  학년·이메일·그때 적은 고민은 접수번호로 조회한다. 번호가 틀려도 신청은 받고,
  관리자 목록에 `대조 실패` 로만 표시한다 — 번호 하나 때문에 신청을 놓치는 쪽이 더 나쁘다.
- **정원** — 화면과 `create_class_application()` 안에서 두 번 막는다. 화면에서만 막으면
  마지막 자리를 동시에 누른 두 명이 둘 다 통과한다(하루 상한에서 겪은 문제와 같다).
  관리자가 **취소한 신청을 되살릴 때**도 같은 반 잠금 아래에서 정원과 같은 연락처를 본다
  (`set_application_status`, 0018) — 취소한 자리에 새 사람을 받은 뒤 되살리면 정원을 넘기 때문이다.
- **한 연락처에 한 자리** — 같은 반에 같은 학부모 번호의 살아 있는 신청이 있을 때, 이름도 같으면 응답만 유실된
  재시도로 보고 그 신청을 돌려준다(알림은 다시 안 보낸다). 이름이 다르면 `PHONE_TAKEN` 으로 막고 그렇다고
  말한다(0019) — 예전에는 앞 학생의 신청을 돌려줘서, 새 학생은 명단에 없는데 성공 화면과 알림이 나갔다.
  앞 학생의 이름은 알려 주지 않는다. 형제 · 자매는 그 번호로 연락할 때 사람이 받는다.
  새 신청인지는 앱이 미리 뽑아 넘긴 id 를 DB 가 그대로 돌려주는지로 가린다. 알림은 새 신청일 때만 간다.
- **결제** — 페이지에 계좌를 올리지 않는다. 신청이 들어오면 팀에게 알림 메일이 가고,
  남겨 준 학부모 번호로 사람이 카카오톡을 보낸다.
- **알림 메일이 실패하면** 그 결과를 신청 행에 적는다(`alert_error`, 0013). 예전에는
  서버 로그 한 줄로만 남아서, 메일이 안 오면 신청이 있다는 사실 자체를 아무도 몰랐다 —
  "메일이 안 왔으니 신청도 없겠지" 가 가장 비싼 오해다. 이제 `/admin/applications` 의
  그 신청 옆에 빨갛게 뜨고, `/setup` 의 '신청 알림 기록' 이 건수를 알려 준다.
  다시 보내는 길은 두지 않았다 — 신청 상태를 '연락함' 으로 옮기면 경고가 사라진다.
  사람이 직접 연락한 것이 곧 해결이기 때문이다.
- **증빙** — 튜터 성적 증빙은 비공개 버킷 `tutor-proof` 에 넣고 볼 때마다 서명 URL 을 새로 만든다.
  버킷을 공개로 열지 않는 이유는 주소가 한 번 새면 계속 열려 있기 때문이다.
  **올리기 전에 이름·수험번호를 가릴 것.**
- **보관** — 신청 정보는 90일 뒤 크론이 행 자체를 지운다(사진처럼 파일만 지우는 게 아니다).

페이지는 학생이 이미 손에 쥔 것에서 시작한다 — 9월에 보낸 피드백 문서의 소제목을 그대로
보여주고, "그 문서에 못 쓴 게 하나 있다"로 넘어간다.

반 정보와 수강료는 **카드(`/class`)와 신청 화면이 같은 부품을 쓴다**(`ClassMeta` · `PriceBlock`).
한 줄로 이어 붙이면 학생이 필요한 값을 못 찾으므로 이름표를 붙여 줄을 나누고, 수강료는
총액 하나만 크게 두고 무엇이 포함되는지를 바로 아래 체크 목록으로 편다 —
모의고사와 스터디룸이 값에 들어 있다는 사실이 이 반의 가장 강한 근거다.
관리자가 적은 `price_note` 한 줄을 가운뎃점으로 잘라 항목을 만든다.

화면 오른쪽 아래에는 챗봇 **관찰이**가 떠 있다(`ClassBuddy`). 이 페이지는 위에서 아래로 길게
읽는 글이라, 다 읽고 나서야 "어디로 물어보지 · 신청은 어디서 하지"가 생기는데 그 답은 맨 아래에만
있었다. 관찰이는 읽는 도중 어디서든 그 두 가지를 하게 한다 — 오픈채팅방으로 보내거나,
개설 클래스 자리(`#classes`)로 데려다 놓는다.

- **묻는 말을 고르게 한다.** 무엇이든 적을 수 있는 입력창은 두지 않는다. 답할 사람이 없는
  입력창은 물어본 사람을 기다리게만 한다. 물어볼 수 있는 것만 눌러서 물어보게 한다.
- **말과 주소는 전부 `class-copy.ts` 의 `BUDDY` 에 있다.** 질문을 늘리려면 `asks` 에 한 덩어리를
  더하면 되고, `action.kind` 가 `'link'` 면 새 창으로, `'scroll'` 이면 같은 화면 안에서 움직인다.
- **말투는 학부모님 기준이다.** 읽는 사람은 학생만이 아니다. 수강료를 내고 반을 고르는 쪽이
  학부모님이라, 관찰이도 페이지 본문과 같은 존댓말로 말한다.
- **곁의 한마디(`hint`)는 말풍선이 닫혀 있는 내내 떠 있다.** 한 번 보여주고 마는 것이 아니다 —
  페이지가 길어서, 다 읽고 내려온 뒤에야 "그래서 어디로 물어보지" 가 떠오르기 때문이다.
  열면 사라지고, 닫으면 잠시 뒤 다시 떠오른다.
- **마스코트는 그림 파일이 아니라 SVG 곰이다**(`ClassBuddy` 의 `<Mascot>`, 색·크기는
  `globals.css` 의 `.buddy`). 배율마다 흐려지지 않고, 눈을 깜빡이거나 말풍선이 열릴 때 웃는 눈으로
  바꿀 수 있다. 옷 색은 새로 만들지 않고 이미 쓰던 빨간펜(`--mark`)을 그대로 쓴다.
  끝없이 도는 움직임은 `prefers-reduced-motion: no-preference` 안에만 둔다 — 바깥의 전역 규칙은
  시간을 0.01ms 로 줄이는데, 무한 반복에 그걸 걸면 멈추는 게 아니라 떨린다.
- **오픈채팅방 버튼은 새 창이 막혀도 열린다.** 이 페이지는 카카오톡으로 퍼지고, 카카오톡 안의
  브라우저는 `target=_blank` 를 막기도 한다. 새 창이 안 열리면 이 화면에서 그대로 연다 —
  눌렀는데 아무 일도 안 일어나는 것이 가장 나쁘다.
- **`#classes` 의 id 와 `BUDDY` 의 `href` 는 같이 고쳐야 한다.** 한쪽만 고치면 버튼이 조용히
  아무 데도 안 간다.

스크롤 등장 효과(`Reveal`)는 **자바스크립트로 DOM 을 건드리지 않는다.** 예전에는 React 보다
먼저 도는 스크립트가 `<html>` 에 `js` 를 붙였는데, 그러면 서버가 그린 class 와 하이드레이션
시점의 class 가 달라 모든 방문자의 콘솔에 하이드레이션 불일치 오류가 찍혔다 — 고칠 수 없는
가짜 오류가 진짜 오류를 덮는다(`suppressHydrationWarning` 으로도 안 잡힌다). 지금은 숨기는
규칙을 CSS 에 그냥 두고, 자바스크립트가 꺼져 있을 때만 `<noscript>` 안의 규칙이 살아나
도로 보이게 한다(`app/layout.tsx`). 브라우저가 알아서 하는 일이라 서버와 클라이언트가
어긋날 자리가 없다. 숨기는 규칙이 CSS 전역에 있으므로 푸는 것도 루트에 둔다 —
`/class` 에만 두면 나중에 다른 화면에서 `Reveal` 을 쓰는 순간 안전장치만 빠진다.

시험지 사진은 접수일 + 30일에 지워진다. 학생이 적어 준 접수번호로 튜터가 그 시험지를 다시
펴 보려면 그 전에 신청이 들어와야 한다 — 모집 메일을 미룰수록 연결 고리가 한 명씩 사라진다.

## 성적 관리 (/lms)

수업이 실제로 돌기 시작하면 필요한 것이 바뀐다. `/apply` 와 `/class` 는 **한 번 받고 끝나는**
흐름이다. 여기는 반대로 **쌓인다** — 같은 학생이 회차를 거듭하며 어디서 무너지는지가
이 서비스가 파는 것이고, 그래서 표를 나눈 기준도 '무엇이 반복되는가' 하나다.

**2026-09-17 부터 수학 실전 모의고사 수업이다. 학생은 전부 미적분을 고른다.** 국어 시절의
문항표 짜기 · 선택과목(화작/언매) · 영역 코멘트는 없어졌고, 대신 시험이 끝난 뒤 학생이 시험지와
질문을 올리고 튜터가 답을 달아 **PDF 로 보내는** 흐름이 생겼다 (`0015_lms_math.sql`).
학생이 올린 시험지 사진에서 학생 답을 읽어 **채점을 저절로 채우는** 것은 `0016_lms_photo_grading.sql` 이다.

```
lms_users            사람 (관리자 · 튜터 · 학생)             안 반복됨
lms_courses          반                                      안 반복됨
lms_exams            시험 회차 · 답 달 기한(다음 수업 날)     반마다 반복
lms_exam_questions   정답표 (번호 · 배점 · 정답 · 단원)       회차마다 30줄
lms_attempts         학생 한 명의 한 회차 · 제출 · 답변 PDF   학생 × 회차
lms_answers          문항 하나의 정오와 학생이 쓴 답         응시 × 문항
lms_attempt_photos   학생이 올린 시험지 사진                  응시 × 장
lms_concerns         문항별 질문 하나와 튜터의 답 하나        응시 × 문항
lms_photo_reads      사진 읽기 한 판 (읽은 답 · 상태 · 횟수)   응시마다 한 줄
```

### 한 회차가 흘러가는 순서

1. **튜터** — 반에서 회차를 만든다. 1–30번이 배점과 함께 바로 깔린다. 정답표 사진을 올리거나
   한 줄로 쳐서 정답을 채운다. 단원은 원하면 붙인다.
2. **튜터** — 시험을 본 뒤 회차를 **학생에게 열림** 으로 바꾼다.
3. **학생** — `/lms/me` 에서 그 시험을 열어 **시험지 사진**을 올리고, 문항마다 막힌 것을 적어
   **제출**한다. '시험 전체' 자리가 따로 있다 — 시간 배분처럼 어느 한 문항의 이야기가 아닌 것이 꼭 나온다.
   사진을 다 올리고 30초가 지나면 서버가 사진에서 학생 답을 읽어 **채점을 채운다** (아래 「사진으로 자동 채점」).
4. **튜터** — 첫 화면(`/lms/tutor`)의 **답을 기다리는 학생**이 기한 순으로 늘어서 있다. 열어서
   질문마다 글로 답하거나 **손으로 쓴 풀이를 찍어 붙인다**. 채점 화면에서는 사진이 매긴 채점을 보고,
   노랗게 표시된 **확인할 문항**만 사진을 보며 매긴다.
5. **튜터** — 다 달면 **저장하고 PDF 보내기**. 답변 PDF 가 저장되고 학생 메일로 첨부돼 간다.
   채점이 끝나 있으면 점수 · 30칸 정오표 · 총평이 함께 들어가고, 학생 화면에도 점수가 열린다.
6. **학생** — 메일이나 `/lms/me` 에서 PDF 를 받는다. 이 시험의 사진 · 질문은 이때부터 잠긴다.
   튜터는 답을 고쳐 **다시 보낼** 수 있고, 학생은 새 PDF 를 받는다.

### 시험지 모양은 정해져 있다 — 배점을 넣지 않는다

수능 수학(공통 + 선택)의 틀을 실전 모의고사도 그대로 따른다. 번호만 알면 나머지가 정해진다.

| 번호 | 구간 | 형식 | 배점 |
|---|---|---|---|
| 1–2 · 3–8 · 9–15 | 공통 | 5지선다 | 2 · 3 · 4 |
| 16–19 · 20–22 | 공통 | 단답형 (0–999) | 3 · 4 |
| 23 · 24–27 · 28 | 미적분 | 5지선다 | 2 · 3 · 4 |
| 29–30 | 미적분 | 단답형 | 4 |

공통 74 + 미적분 26 = 100. 이 표는 `src/config/lms.ts` 의 `BANDS` 하나다 — 정답표 화면 · 채점 ·
집계 · PDF 가 전부 여기서 번호의 성격을 읽는다. 그래서 튜터가 고칠 칸이 없고 줄을 더하거나 지울
단추도 없다. 다만 회차를 만들 때 배점을 문항표에 **베껴 둔다**(`points`) — 나중에 틀이 바뀌어도
(2028 수능처럼) 지난 회차 점수는 그대로다.

**단원은 선택이다.** 수능형 시험지는 번호만으로 단원이 정해지지 않고(공통 1–22 는 수학Ⅰ·Ⅱ 가
섞여 나온다), 정답표 사진에도 대개 없다. 붙인 문항만 단원별 정답률에 들어가고, 안 붙인 문항은
점수에만 들어간다 — 짐작해 채운 단원은 단원 집계를 조용히 거짓말로 만든다. 번호에 맞지 않는
단원(공통 문항에 미적분 단원)은 화면 · 서버 · 사진 읽기가 모두 버린다. 단원 목록은 `UNITS` 이고,
이미 쓰인 코드를 지우면 그 문항이 미아가 되므로 지우지 않는다.

**점수를 쪼개 보는 칸은 셋이다** — 공통/미적분 · 배점(2 · 3 · 4점) · 단원. 셋 다 번호와 문항표에서
저절로 나오므로 따로 입력할 것이 없다. 4점 정답률이 이 수업에서 가장 먼저 보는 숫자다.

### 정답을 넣는 세 가지

- **정답표 사진** — 시험지 뒤의 정답표나 해설지 첫 장을 찍어 올리면 초안을 채운다
  (`lib/lms/ocr.ts`, Claude Opus 5). 선택과목이 셋 다 적힌 정답표라면 23–30번은 **미적분 것만**
  읽는다. 읽은 것만 말하고, 못 읽은 번호와 **두 가지로 읽힌 번호**(비워 둔다 — 둘 중 하나를 고르면
  틀린 쪽을 고른 날 조용히 틀린 채점이 된다)를 따로 짚는다. 저장하지 않고 칸에 채우기만 한다.
  사진은 어디에도 남기지 않는다.
- **한 줄로 넣기** — `3 5 2 4 1 … 12 7 24 …` 처럼 친다. 5지선다 구간은 `35241` 처럼 붙여 써도 되고,
  모르는 칸은 `-` 로 자리만 채운다. 그 자리에 올 수 없는 값(5지선다에 7)은 버리지 않고 빨갛게
  남긴다 — 조용히 비우면 그 뒤로 번호가 한 칸씩 밀린 줄도 모른다 (`lib/lms/answer-line.ts`).
- **직접 누르기** — 5지선다는 ①–⑤ 단추, 단답형은 숫자 칸.

구조화 출력(`output_config.format`)이 보장하는 것은 **키와 자료형까지**다. SDK 가 `enum` 과 범위를
설명 문구로 낮추기 때문에 모델이 31번이나 5지선다 6번을 줄 수 있다. 값 검사는 `normalizeExtracted()`
가 다시 한다 — 거기가 진짜 방어선이고, 그래서 API 호출과 떼어 두었다(키 없이도 확인할 수 있다).
요청에는 `fallbacks: "default"` 를 붙였다 — 드물게 안전 분류기가 거절하면 알맞은 다른 모델로 한 번 더
돈다. 그래도 거절되면 '직접 넣어주세요' 라고 말한다. `ANTHROPIC_API_KEY` 가 없으면 이 기능만 꺼진다.

### 채점 — 학생 답을 넣으면 저절로 매겨진다

학생이 쓴 답을 넣으면 정답과 맞춰 O/X 가 찍힌다. 한 줄 넣기도 된다(`-` 는 안 쓴 답 = 틀림).
답 없이 O/X 만 눌러도 된다 — 수업 중에 종이를 넘기며 빠르게 매길 때는 그쪽이 빠르다.

**정답을 고치면 적어 둔 학생 답으로 다시 매긴다** (`save_answer_key`). 정답을 잘못 넣은 채 채점을
끝냈다가 고치는 일이 실제로 생기는데, 그때 채점을 처음부터 다시 하게 두면 아무도 안 한다.
O/X 만 찍은 문항은 무엇을 골랐는지 몰라 그대로 둔다 — 화면이 그렇게 말한다.

**아직 안 매긴 문항은 오답이 아니다.** `lms_answers` 에 행이 없는 문항은 '아직'이고, 채점이
끝나지 않은 응시는 평균과 석차에서 빠진다 — 섞으면 채점하다 만 회차가 0점으로 보인다.
평균 · 추이는 여전히 `득점 / 배점합 × 100` 이다. 수학은 늘 100점이지만, 틀이 바뀐 회차가 섞여도
평균이 거짓말을 하지 않게 둔다.

### 사진으로 자동 채점 (0016)

학생이 시험지 사진을 올리면 서버가 사진에서 **학생이 고른 · 적은 답**을 읽고(Claude Opus 5, 문제는 풀지
않는다) 정답표와 맞춰 채점을 채운다. 튜터가 학생 답 30개를 옮겨 적던 일이 '확인할 문항만 보기' 로 줄어든다.

- **확실히 읽힌 것만 매긴다.** 모델은 문항마다 `sure` 를 준다. 둘 다 동그라미 · 흐림 · 사진마다 다르게
  읽힘(답안지와 문제지가 다름) · 그 번호에 올 수 없는 값이면 매기지 않고 **확인할 문항**으로 남긴다.
  채점이 덜 끝난 것으로 남으니 일괄 공개에도, 답변 PDF 의 점수에도 안 들어간다. 확실한 빈칸은 틀림이다
  (손으로 매길 때도 그렇다). 튜터 화면은 확인할 문항을 노랗게 두르고 읽힌 값을 **넣기** 한 번으로 넣게 한다.
- **튜터가 매긴 채점은 덮지 않는다.** 채점 화면에서 한 문항이라도 매겨 저장하면 튜터 채점이 된다
  (`answers_source`). 그 뒤로 사진을 다시 읽으면 다른 문항만 짚고, 튜터가 **읽은 답으로 다시 매기기**를
  눌러야 바뀐다. 점수를 공개한 응시는 그것도 안 된다.
- **오래 열어 둔 채점 화면으로는 그냥 저장되지 않는다.** 화면이 그릴 때 본 판 — 정오와 정답표 — 을 같이
  보내고, `save_grading` 이 응시를 잠근 뒤 지금 것과 견준다(`lib/lms/grading-snapshot.ts`, 0017). 그사이 학생이
  사진을 바꿔 사진 채점이 비워졌거나 새로 채워졌거나, 정답표가 고쳐졌으면 아무것도 쓰지 않고 멈춘다 — 안 막으면
  사라진 옛 사진의 점수가 되살아나 공개되거나, 다시 매긴 정오를 옛 O/X 가 덮는다. 튜터가 방금 매긴 것은 화면에
  그대로 두고 바뀐 문항 번호를 짚는다. 확인하고 한 번 더 누르면 그 화면의 채점으로 저장된다.
  시각(`updated_at`)으로 견주던 때(0016)는 학생이 질문을 제출하기만 해도 거절돼서 내용으로 바꿨다.
  **새로 고쳐 바뀐 채점 보기**를 누르면 채점표를 새 판으로 다시 붙인다 — 화면을 새로 고쳐도 브라우저 쪽 상태는
  남으므로, 받은 판이 바뀌면 매긴 것 · 총평 · 견줄 판을 같이 버린다. 안 그러면 옛 O 가 남은 채로 저장 검사를 통과한다.
- **사진이 바뀌면 옛 사진의 채점은 그 자리에서 사라진다.** 사진 행을 넣고 지우는 트랜잭션 안에서
  트리거가 사진으로 매긴 비공개 채점을 비운다 — 새 읽기가 늦거나 실패하거나 횟수 상한에 걸려도 옛 점수가
  공개되는 일이 없다. 읽은 결과를 적을 때와 채점에 옮길 때마다 지금 사진 묶음과 같은지 다시 보고,
  다르면 버린다(`PHOTOS_CHANGED`). 일괄 공개(`publish_grades`)와 답변 PDF 보내기(`mark_feedback_ready`)도
  응시를 잠근 채 지금 채점을 다시 본다 — PDF 를 만든 뒤 채점이 바뀌었으면 `REGRADED` 로 멈춘다.
- **한 장씩 올리는 동안 매번 읽지 않는다.** 사진이 바뀔 때마다 읽기 번호를 올리고 30초 조용히 기다린다.
  그 사이 또 바뀌면 앞의 읽기는 시작하지 않는다. 늦게 끝난 옛 읽기는 결과를 버린다.
  학생 쪽 변화로 부르는 횟수는 응시당 8번까지다(튜터의 **다시 읽기**는 상한이 없다).
- **사진은 4장씩 나눠 보낸다.** 긴 변 2000px 사진은 한 장이 입력 4천 토큰쯤이라 여러 장을 한 번에 보내면
  낮은 요금 등급의 분당 한도를 혼자 넘는다. 요청은 둘씩 겹쳐 보내고, 같은 문항이 여러 장에서 읽히면 맞춰 본다.
- **시간을 넘기지 않는다.** 읽기는 응답을 보낸 뒤 서버 함수 안에서 돈다(`after()`, 상한 300초).
  SDK 의 자동 재시도는 끄고, 사진 받기 · 요청 · 재시도 기다림을 하나의 마감 시각 안에서 센다
  (`lib/lms/retry.ts`) — 넘길 것 같으면 보내던 요청도 끊고 `TIMEOUT` 을 적는다. 그래도 서버가 끊겨
  '읽는 중' 에 10분 넘게 머물면 화면이 **멈춤**으로 보여 주고, 매일 새벽 정리가 다시 읽는다
  (재시도할 만한 실패만, 사흘 안, 12번까지).
- **화면은 끝나기를 기다린다.** 학생 · 튜터 화면이 작은 상태 주소(`read-status`)만 몇 초마다 묻고,
  끝나면 한 번 새로 그린다. 서버가 '멈춤' 이라 판정하는 때보다 오래 지켜본다. 튜터가 채점을 매기던 중이면
  새로 그리지 않고 알리기만 한다. 학생 화면은 흐려서 못 읽은 사진에 **다시 찍어 주세요** 를 붙인다
  (학생에게는 읽은 답을 보이지 않는다).
- **비용.** Opus 5 는 입력 100만 토큰에 5달러다. 시험지 12장이면 입력 약 5만 토큰이라 한 번 읽는 데
  대략 0.3–0.4달러, 반 20명이면 한 회차 7달러 안팎이다. 사진을 바꿀 때마다 다시 읽는다.
- **개인 정보.** 학생 시험지 사진이 Anthropic API 로 간다. 학생 화면에 그렇게 적었고, 모델에게는 이름 ·
  학교를 옮겨 적지 말라고 했다. `ANTHROPIC_API_KEY` 를 비우면 이 기능만 꺼진다.

### 시험 뒤의 질문과 답

학생 질문은 **한 문항에 한 줄**이다(`unique (attempt_id, question_no)`). 같은 문항 이야기가 두 줄로
흩어지면 답도 둘로 흩어진다. 화면은 같은 번호를 두 번 못 고르게 하고, 그래도 오면 서버가 합친다.
글자 수 상한(질문 2,000 · 답 8,000)은 화면과 DB 가 같은 값을 본다. DB 는 글자를 code point 로 세므로
서버도 이모지를 한 글자로 센다.

- **제출해야 튜터의 할 일에 오른다.** 임시 저장은 목록에 안 올린다 — 쓰다 만 것까지 세면 할 일이 부풀어 보인다.
  튜터 화면은 제출 전 질문도 보여 주되 '아직 제출 전' 이라고 적는다. 제출한 뒤 학생이 고치거나 더한
  질문에는 **제출 뒤에 고친 질문** 딱지가 붙는다(`updated_at` 은 학생이 고친 시각만 담는다).
- **답이 달린 질문은 학생이 못 고친다**(DB 가 막는다). 질문이 바뀌면 달아 둔 답이 엉뚱한 말이 된다.
- **'다 단 것' 은 두 번 확인한다.** 화면이 보내기를 막고, DB 가 한 번 더 본다(`mark_feedback_ready`).
  같은 응시를 잠근 채로 ① 답 없는 질문이 있으면 멈추고 ② PDF 에 담긴 질문과 지금 질문 목록이
  다르면 멈춘다 — 튜터가 화면을 연 사이 학생이 질문을 더했다면, 그 질문은 PDF 에 없는데 학생 쪽은
  잠겨 버린다. 학생 질문 저장(`save_concerns`)도 같은 줄을 잠그고 줄을 선다.
- **답은 글이든 사진이든 된다.** 수식은 글로 치는 것보다 종이에 쓰고 찍는 편이 빠르고 정확하다.
  사진만 붙여도 답한 것으로 친다.
- **저장과 보내기가 한 단추다**(`저장하고 PDF 보내기`). 따로 두면 마지막 답을 쓰고 '보내기' 만 눌렀을 때
  그 답이 빠진 PDF 가 나간다. 누르기 전에 무엇이 들어가는지(질문 수 · 점수 여부 · 메일 주소)를 한 번 묻는다.
- **메일은 실패해도 PDF 는 나간 것이다.** 결과를 응시 행에 적는다(`mailed_at` · `mail_error`) —
  신청 알림(0013)과 같은 태도다. 학생 계정에 메일이 없거나 메일 설정이 없으면 그 이유가 튜터 화면과
  회차 표에 뜨고, 학생은 화면에서 받는다. 계정 목록 · 회차 표에 **메일 없음** 이 미리 보인다.
  학생이 답장하면 담당 튜터 메일로 간다(`replyTo`).
- **보내면서 점수를 연다.** PDF 에 이미 점수가 들어 있는데 화면에는 '공개 전' 이면 학생이 헷갈린다.
  채점이 덜 끝났으면 점수는 PDF 에서 빠지고 공개도 안 한다. 공개는 '보냄' 표시와 같은 잠금 안에서 한다.
- **점수가 든 PDF 는 판을 견주고 보낸다.** PDF 를 만들 때 읽은 판(정오 · 정답표)이 지금도 같을 때만 '보냄' 으로
  표시한다(아니면 `REGRADED`). 이미 공개한 응시에 다시 보낼 때도 같다(0018) — 예전에는 새로 공개할 때만 봐서,
  다시 보내는 사이 채점이 바뀌면 옛 점수가 든 PDF 가 나갔다.
- **답을 보낸 시험의 사진은 DB 가 막는다**(0018). 학생 쪽은 시작할 때 한 번 보는데, 사진을 올리는 사이 튜터가
  보내기를 끝낼 수 있다. 사진을 넣고 지우는 트리거가 응시를 잠근 채 다시 보고 `LOCKED` 로 거절한다.

### 답변 PDF

`lib/lms/pdf/feedback-pdf.ts` 가 만든다 — 머리말 · 점수 상자(총점 · 공통 · 미적분) · 틀린 문항 ·
**30칸 정오표**(틀린 칸에 '내가 쓴 답 → 정답') · 질문과 답 카드(문항 순서, '시험 전체' 는 맨 뒤) ·
손풀이 사진 · 총평 · 쪽 번호. 긴 답은 쪽을 넘겨 흐른다. 튜터는 보내기 전에 **PDF 미리 보기**로
지금 저장된 내용 그대로 확인하고, 보낸 뒤에는 **보낸 PDF 보기**로 학생이 받은 파일을 연다.

- **pdf-lib + fontkit 2.** pdf-lib 이 원래 짝으로 쓰는 `@pdf-lib/fontkit`(fontkit 1)은 한글 폰트를
  잘라 넣을 때 글자를 군데군데 빈칸으로 만든다 — '3주차 · 강대K' 가 '대' 한 글자만 남았다. 통째로
  넣으면 굵기 둘에 2MB 다. fontkit 2 는 잘라 넣어도 정확하고 같은 PDF 가 20KB 남짓이다. 다만
  pdf-lib 이 부르는 `encodeStream()` 이 fontkit 2 에 없어서 그 한 자리만 흉내 낸다(`pdf/fontkit.ts`).
- **글꼴은 Pretendard 원본 그대로**(`assets/fonts`, SIL OFL 1.1 — 라이선스 파일을 옆에 둔다).
  사이트와 같은 글꼴이다. 글자를 덜어 낸 파일을 같은 이름으로 배포하면 OFL 의 '예약된 이름' 조항에
  걸려서 원본을 쓴다(한 벌 2.7MB). PDF 에 넣을 때 쓰인 글자만 잘라 넣는 것은 괜찮다.
  서버 함수 묶음에 폰트가 따라가도록 `next.config.ts` 의 `outputFileTracingIncludes` 에 적어 뒀다.
- **폰트에 없는 글자** — 이모지는 조용히 빼고, 나머지는 □ 로 자리를 남긴다. 수식 기호(∫ √ π ≤ ①)는
  Pretendard 에 있다. 깨진 풀이 사진이 섞여도 PDF 전체가 멈추지 않고 그 자리에 적는다.
- **줄은 어절 단위로 넘긴다** — 사이트의 `word-break: keep-all` 과 같은 결. 한 줄보다 긴 어절만 글자로 자른다.

### 파일 — 시험지 사진 · 풀이 사진 · PDF

비공개 버킷 `lms-files` 에 응시 단위로 둔다(`attempts/{응시}/…`). 접수 흐름의 `exam-papers` 와 섞지
않는다 — 저건 30일 뒤 지우고 주인 없는 사진을 매일 치우는 버킷이라 수업 중인 사진이 사라진다.
볼 때마다 한 시간짜리 임시 주소를 만든다. 사진은 브라우저가 긴 변 2000px JPEG 로 줄여 한 장씩
보내고, 서버는 확장자가 아니라 **파일 첫 바이트**로 JPEG 인지 본다.

**DB 는 줄을 지울 때 파일을 지워 주지 않는다.** 회차 · 반 · 학생 계정을 지우면 앱이 **파일을 먼저**
지우고 줄을 지운다. 파일 삭제가 실패하면 줄도 안 지우고 멈춘다 — 이름과 필기가 찍힌 시험지 사진이
주인 없이 남는 것이 더 나쁘다. 학생이 사진 **한 장**을 지울 때만 줄을 먼저 지운다 — 답을 보낸 시험이면 DB 가
거절하는데, 파일부터 지우면 거절돼도 사진은 이미 사라진다. 그 뒤 파일 지우기가 실패하면 로그에 남는다. 새 파일을 올렸는데 줄을 못 만들면 그 파일을 도로 지운다.
사진 · PDF 이름에는 매번 새 id 를 쓴다 — 다시 보낸 PDF 가 지난 파일을 덮어쓰다 실패하면 학생이
반쪽 파일을 받는다.

### 국어에서 넘어올 때 (0015)

`0015_lms_math.sql` 은 국어 시절의 회차 · 문항표 · 응시 · 정오 · 영역 코멘트와 학생별 선택과목을
**지우지 않고** `lms_legacy_*` 표로 옮긴 뒤 수업 표에서 뺀다. 반 · 수강 · 계정은 그대로라 같은 반에서
수학 수업을 이어 간다. 옮기기는 옛 모양(`area_code` 열)이 남아 있을 때만 돌고, 한 번에 보낸 문장은
한 트랜잭션이라 중간에 실패하면 아무것도 안 바뀐다. 여러 번 돌려도 보관본이 두 벌이 되지 않는다.
**SQL 을 먼저 돌리고 배포한다** — 새 코드는 옛 모양의 표를 읽지 못한다(`/setup` 의
'수학 수업 표' 가 빨간불이면 아직이다).

### 로그인

역할 셋(관리자 · 튜터 · 학생)이 각자 계정으로 들어온다. Supabase Auth 를 붙이지 않았다.
이 프로젝트는 **브라우저가 Supabase 에 직접 붙지 않고**(anon 키가 아예 없다) 서버만 DB 를
만지는데, 로그인만을 위해 그 원칙을 깨면 RLS 정책을 새로 짜야 하고 구조가 통째로 흔들린다.
그래서 계정표를 직접 두고, 쿠키는 이미 쓰던 HMAC 서명 방식(`lib/admin.ts`)을 넓혔다.

- 비밀번호는 scrypt 해시로만 저장한다. 관리자도 볼 수 없고, 잊으면 새로 발급한다.
- **역할은 쿠키에 담지 않는다.** 담으면 계정을 정지시켜도 이미 나간 쿠키가 만료될 때까지
  살아 있다. 쿠키에는 사용자 ID 와 세션 열쇠만 넣고 매 요청마다 DB 에서 다시 읽는다.
- **비밀번호를 바꾸면 다른 기기의 로그인이 풀린다.** 비밀번호를 바꾸거나 새로 발급할 때마다 세션 열쇠
  (`lms_users.session_key`, 0018)를 새로 뽑고, 쿠키의 열쇠가 다르면 로그인이 풀린다. 본인이 바꾼 브라우저에는
  새 열쇠로 다시 들여보낸다. 없으면 잃어버린 기기의 로그인이 30일 동안 산다.
- **처음 받은 비밀번호를 안 바꾼 동안은 쓰기도 막힌다.** 화면만 막으면 발급된 비밀번호를 아는 사람이 서버 함수를
  바로 부를 수 있다. 비밀번호 바꾸기만 `assertSignedIn()` 으로 들어온다.
- 관리자가 만들어 준 첫 비밀번호로 들어온 사람은 바꾸기 전에는 다른 화면으로 못 간다.
- 첫 관리자는 닭과 달걀이라 `/lms/setup` 이 **기존 `ADMIN_PASSWORD` 잠금으로** 열린다.
  계정이 하나라도 생기면 그 문은 영영 닫힌다. 들어가는 문은 `/admin` 위쪽의
  **성적 관리** 메뉴다 — 같은 도메인 안에서 이동하므로 잠금이 그대로 따라간다.
- 서명 열쇠는 `LMS_SESSION_SECRET`, 없으면 `ADMIN_PASSWORD` 를 쓴다. 둘 다 없으면 안 열린다.
- 아이디는 **소문자로만** 저장된다(`0009`). 앱은 늘 소문자로 내려 찾으므로, Table Editor 로
  대문자가 섞인 줄을 직접 넣으면 그 계정은 영영 로그인이 안 되고 이유도 안 보인다 —
  그래서 DB 가 아예 거절한다. 찾는 쪽을 `ilike` 로 바꾸지 않은 것은 아이디에 `_` 를
  허용하고 있어서다(LIKE 에서 `_` 는 아무 글자 하나를 뜻한다).

**점수 공개는 두 겹이다.** 회차가 '학생에게 열림' 이어도 학생에게는 *자기 채점을 공개한 것만*
보인다. 채점 화면에서 '저장하고 점수 공개' 를 누르거나 답변 PDF 를 보내야 그 학생이 볼 수 있다 —
매기다 만 점수가 학생에게 보이는 것이 이 화면에서 가장 나쁜 일이다. 회차를 다시 '준비 중' 으로
돌리면 그 회차의 점수 · PDF 도 학생에게서 닫힌다.

튜터는 남의 반을 못 본다. 주소창에 다른 반 id 를 넣어도 `courseVisibleTo()` 가 막는다 —
화면이 아니라 서버 함수 · 파일 라우트 · 페이지 진입점 모두에서 확인한다. 학생 쪽 쓰기는 응시 id 를
받지 않고 **회차 id 와 로그인한 사람으로** 응시를 찾는다 — 남의 응시를 가리킬 길 자체가 없다.

### 되풀이를 줄이는 것들

- **한 줄로 넣기** — 정답 30개도, 학생 답 30개도 한 번에 친다.
- **정답을 고치면 다시 매김** — 위 「채점」.
- **회차 일괄 공개** — 채점이 끝난 학생만 공개하고, 몇 명이 남았는지 말해 준다.
- **답을 기다리는 학생** — 튜터 첫 화면에 기한 순으로. 기한이 지났거나 오늘이면 빨갛다.
- **답 달 기한** — 회차를 만들 때 비우면 시험 날 + 7일(주 1회 수업의 다음 수업 날).
- **튜터가 자기 반 학생 비밀번호 재발급** — 관리자만 할 수 있게 두면 학생이 비번을 잊은 날
  수업이 멈춘다. 대신 `studentVisibleTo()` 로 자기 반 학생인지 반드시 확인한다.
- **성적 CSV** — 공통/미적분 · 배점별 · 단원별 정답률을 고정된 열 순서로. 맨 앞에 BOM 을 붙인다.
  없으면 한국어 윈도우 엑셀이 EUC-KR 로 읽어서 이름이 전부 깨진다.
- **되돌릴 수 없는 것에는 확인을 붙였다.** 반 · 회차 · 계정 삭제는 무엇이 함께 사라지는지(시험지 사진 ·
  답변 PDF 까지)를 문구에 적는다 — "정말 삭제하시겠습니까?" 는 아무 정보가 없어서 아무도 안 읽는다.

### 시험

```bash
npm test        # DB 없이. 1초 안에 끝난다
npm run test:db # 진짜 DB 에 붙여 수업 한 회차를 통째로
```

**`npm test`** 는 DB 없이 도는 것만 본다 — 점수를 어떻게 세는가, 답을 어떻게 읽는가(한 줄 넣기 ·
동그라미 숫자), 사진에서 온 정답을 어떻게 거르는가, 사진 여러 장의 학생 답을 어떻게 합치는가,
비밀번호를 어떻게 다루는가, 답변 PDF 가 실제로 만들어지는가(쪽 넘김 · 깨진 사진 · 이모지).
틀리면 사람이 손해를 보는데 화면만 봐서는 틀린 줄 모르는 것들이다. 모델 요청은 이 과정 안에 띄운
가짜 서버(127.0.0.1)로 보내 **마감 시각을 넘지 않는지**(응답 없음 · 긴 Retry-After · 연속 503)를 본다.
밖으로는 나가지 않는다.

**`npm run test:db`** 는 붙여 봐야 아는 것을 본다 — 제약이 실제로 거는가, 연쇄 삭제가 도는가,
저장이 실패했을 때 되돌아가는가, 시험지 사진과 답변 PDF 가 줄과 함께 지워지는가, 답이 다 안
달렸을 때 정말 안 보내지는가, 사진이 바뀌면 사진 채점이 사라지고 옛 읽기가 버려지는가, 튜터 채점과
공개한 점수를 안 덮는가. 모델은 이 과정 안에 띄운 가짜 서버다. 실제로 이 시험을 만들다가 채점이
통째로 사라지는 버그(아래)와,
Postgres 18 에서 반을 맡은 튜터를 지우면 안내 대신 오류 화면이 뜨는 문제(18 부터 `23503` 이 아니라
`23001` 로 거절한다)를 찾았다. 붙은 DB 의 **LMS 표와 `lms-files` 버킷을 비우므로** 평소 환경변수를
쓰지 않고 일부러 다른 이름을 본다. 메일 환경변수는 지우고 돈다 — 학생에게 진짜 메일이 가면 안 된다.

```bash
TEST_SUPABASE_URL=https://xxxx.supabase.co \
TEST_SUPABASE_SERVICE_ROLE_KEY=... \
npm run test:db
```

버려도 되는 Supabase 프로젝트를 하나 더 만들어(무료로 된다) `supabase/migrations` 를 번호
순서대로 돌려 두고 그 주소를 넣는다. `TEST_SUPABASE_URL` 이 `SUPABASE_URL` 과 같으면
운영 DB 로 보고 멈춘다 — `.env` 를 통째로 불러 놓고 돌리는 일이 실제로 생긴다.

자격증명이 없으면 실패가 아니라 '이렇게 넣으면 된다' 를 적고 조용히 끝난다. 배포를 막지 않기 위해서다.

시험 틀은 들이지 않았다. 통과·실패를 세고 색을 입히는 스무 줄(`test/assert.ts`)이면 충분하고,
의존성이 하나 늘면 그것도 관리 대상이 된다.

### 저장이 실패하면 반드시 말한다

supabase-js 는 실패해도 예외를 던지지 않고 `{ data, error }` 로 돌려준다. 확인하지 않으면
두 가지가 조용히 일어난다.

- **쓰기** — 저장이 안 됐는데 화면이 '저장했어요' 라고 말한다.
- **읽기** — 못 읽었는데 **빈 목록**으로 둔갑한다. 이쪽이 더 위험하다: 채점 화면이 답안을
  못 읽으면 아무것도 안 매긴 것처럼 보이고, 튜터가 다시 매겨 저장하면 진짜 채점이 그 위에 덮인다.

그래서 LMS 의 모든 DB 접근이 `lib/lms/db.ts` 를 지나고, 거기서 실패하면 던진다.
조용히 틀린 화면보다 시끄러운 오류가 낫다.

예외가 둘 있고 둘 다 이유가 있다. `currentUser()` 는 못 읽으면 '아무도 아닌 것' 으로 친다 —
누구인지 모르는데 통과시키면 잠금이 풀린 것이라, **잠긴 채로 실패해야 한다.**
9월 고민 조회는 실패해도 넘어간다 — 그건 있으면 좋은 것이지, 그것 하나 때문에 채점 화면이
통째로 막히면 안 된다.

채점 저장은 그것만으로 부족했다. 요청 네 번(정오 지우기 → 넣기 → 코멘트 → 응시 갱신)으로
나뉘어 있어서, 두 번째가 실패하면 첫 번째는 이미 끝나 있다 — 매겨 둔 채점이 통째로 사라진다.
실제로 재현했다: **82점 · 정오 45개 → 0점 · 0개, 예외 없음.**

`0012` 가 이것을 DB 함수 하나로 묶었다. plpgsql 함수는 통째로 한 트랜잭션이라 중간에
실패하면 전부 되돌아간다. 이 프로젝트는 정원 초과를 막을 때 이미 같은 방법을 썼다
(`0005` 의 `create_class_application`). 고친 뒤 다시 시험해서 정오 · 점수 · 총평 · 공개
상태가 모두 그대로 남고 예외가 올라오는 것을 확인했다.

수학으로 바뀌며 같은 방식의 함수가 넷 더 생겼다(0015) — 정답표 저장, 학생 질문 저장, 튜터 답 저장,
'다 달았다' 표시. 넷 다 한 번에 여러 줄을 바꾸고, 중간에 끊기면 학생의 질문이나 튜터의 답이 사라지는 자리다.
사진 자동 채점(0016)의 부르기 · 시작 · 마치기 · 옮기기 · 일괄 공개도 같다 — 전부 응시를 먼저 잠그고
(회차 → 응시 → 읽기 · 답안 순서로만 잠근다), 사진을 넣고 지우는 트리거도 같은 응시 행을 먼저 잠근다.
**답안 행을 건드리기 전에 그 응시 행을 먼저 잠근다**는 것이 이 순서의 핵심이다 — 정답표 저장은 여러
응시의 답안을 한꺼번에 다시 매기므로, 회차의 응시를 id 순으로 먼저 잠근 뒤에 답안을 고친다. 답안을
먼저 잡으면 같은 순간 사진을 올리는 트리거와 서로 기다리다 한쪽이 죽는다(정답표 저장이나 사진 올리기
실패). 마이그레이션 시험이 함수 본문에서 이 순서를 확인한다.
`save_grading` 은 넘어온 문항이 **그 응시의 회차 것인지**도 본다 — 다른 회차의 문항 id 가 섞이면 외래키로는
안 걸리고(문항은 있으니까) 점수만 조용히 엉뚱해진다.

### 학기가 쌓이면 터지던 자리

PostgREST 는 조건을 주소줄에 싣는다. `courseSummary()` 는 반의 모든 회차, 모든 학생의 응시를
한 번에 물었는데 — 학생 스무 명이 회차 스무 번을 보면 응시가 400개고, 주소가 15KB 가 되어
그 앞의 프록시들이 414 를 낸다. 한 학기면 닿는 규모다.

`inChunks()` 가 100개씩 나눠 묻고 이어 붙인다. 학생 목록 · 회차 목록도 같다.
나눈 묶음도 끝까지 넘겨 읽는다 — Supabase 는 한 번에 1,000줄까지만 주고 나머지를 말없이
자르기 때문이다. 응시 23개 × 답안 45개(1,035줄, 국어 시절)에서 이미 채점이 끝난 응시가 '덜 매김' 으로
계산됐다. 수학은 한 회차 30줄이라 응시 34개면 같은 자리에 닿는다. `inChunks()` 에 넘기는 조회는 겹치지 않는 열로 정렬해야 한다.

### 처음 켤 때 걸리는 것

**프리뷰 배포와 실제 주소는 서로 다른 도메인이라 로그인이 따라가지 않는다.** 실제 주소에서
`/admin` 에 로그인해도 그 쿠키는 그 도메인에만 붙으므로, 프리뷰 주소의 `/lms/setup` 에서는
로그인한 적이 없는 사람이다. 이때 조용히 로그인 화면으로 넘기면 거기서 로그인해도 `/admin`
으로 갈 뿐 돌아오지 않아서 제자리를 맴돈다. 그래서 그 화면은 넘기지 않고 **왜 못 들어오는지
말해 주고** `/admin/login` 으로 보낸다.

**DB 가 대답하지 않아도 로그인 화면은 뜬다.** 주소와 키는 채워져 있는데 키가 틀렸거나
SQL 을 아직 안 돌렸으면, 예전에는 로그인 화면 자체가 '잠시 문제가 생겼어요' 로 바뀌어서
무엇이 잘못됐는지 볼 방법이 없었다. 지금은 화면이 그대로 뜨고 그 사실만 따로 알려 준다.

다만 **계정 수를 못 세는 동안에는 `/lms/setup` 이 열리지 않는다.** '0명' 과 '못 물어봤음' 은
다르다 — 못 물어본 것을 0명으로 치면 이미 계정이 있는 DB 에 관리자를 하나 더 만들어 준다.

### 화면 만듦새

기둥 폭만 1080px 로 넓히고 재질 · 색 · 글자는 접수 흐름과 하나도 다르지 않게 뒀다.
루트 레이아웃을 고치면 `/apply` · `/class` · `/admin` 이 전부 따라 움직이므로,
`body:has(.lms-page)` 로 **LMS 화면이 떠 있을 때만** 넓어지게 했다.

그래프의 색은 이미 쓰던 두 가지뿐이다 — 파랑이 데이터, 빨강은 '여기를 보라'(약한 단원).
단원마다 색을 달리하면 아홉 가지가 필요한데, 여기서 색이 말해야 하는 건 '어느 단원인가'가
아니라 '얼마나 맞았나'라서(그건 막대 길이가 말한다) 색을 더 쓸 이유가 없다.
빨강은 늘 '약함' 글자 딱지와 함께 나간다 — 색을 구별 못 하는 사람에게 색만으로 말하지 않기 위해서다.
그래프 옆에는 같은 값을 표로도 둔다.

정답률 막대(`RateBars`)는 SVG 가 아니라 HTML 이다. 막대 색을 SVG 속성(`fill`)으로만 적어 두었던
탓에 국어 시절부터 **막대가 통째로 안 보였다** — 숫자만 떠 있어서 아무도 눈치채지 못했다.
`globals.css` 의 `.chart-bar` · `.chart-track` 은 이제 `background-color` 도 함께 칠한다.

### 9월 시험지 피드백과의 연결

학생 계정에 `/apply` 접수번호를 적어 두면, 그때 학생이 **직접 적어 준 고민**이 튜터의 학생
상세와 채점 화면에 함께 뜬다(`lib/lms/intake.ts`). 점수는 무엇이 무너졌는지까지만 말하고,
그때 현장에서 무엇을 하고 있었는지는 거기에만 있다.

사진과 PDF 는 접수일 + 30일에 지워지지만 접수 기록과 고민 답변은 남는다
(`purgeExpiredFiles()` 는 파일만 지우고 행은 `status='purged'` 로 표시만 한다).
그래서 사진이 사라진 뒤에도 이 연결은 계속 읽히고, 화면은 사진이 없다는 것만 알려 준다.

번호가 틀렸거나 접수한 적이 없으면 그냥 안 뜬다 — 모집 페이지에서와 같은 태도로,
번호 하나 때문에 아무것도 못 하게 만들지 않는다.

### 남은 것

- 로그인 시도 횟수 제한이 없다. 서버리스라 메모리에 세는 방식은 무의미하고, 넣으려면
  DB 나 외부 저장소가 필요하다. 계정이 사람 수십 명 규모인 동안은 열어 둔다.
- 학부모 계정은 따로 두지 않기로 했다(2026-09-07 결정). 학생 계정을 함께 쓴다.
  답변 PDF 도 학생 메일로만 간다 — 학부모에게는 사람이 카카오톡으로 전한다(튜터 화면에서 받아 보낼 수 있다).
- 접수번호는 관리자가 손으로 적는다. 이름으로 자동 대조하지 않는다 — 동명이인이 있고,
  틀린 연결이 없는 연결보다 나쁘다.
- **학생이 제출해도 튜터에게 알림 메일은 안 간다.** 튜터 첫 화면의 목록이 할 일이다.
- **시험지 사진 보관 기한이 없다.** 회차 · 반 · 계정을 지울 때 함께 지워지고, 그 전까지는 남는다.
  반을 '종료' 로 바꿔도 남는다 — 무료 저장소(1GB) 기준으로 한 장 1MB 안팎이라 한 학기는 넉넉하지만,
  기한을 정하면 매일 크론에 붙이면 된다.
- **사진 자동 채점은 진짜 모델로 정확도를 재 보지 않았다.** 시험은 가짜 모델로 흐름 · 잠금 · 시간만 본다.
  실제 학생 시험지 몇 장으로 확실(`sure`) 판정이 믿을 만한지 먼저 봐야 한다 — 틀리게 확실하면 튜터가
  안 보는 칸에 틀린 채점이 들어간다.
- **두 연결이 동시에 부딪히는 시험은 못 돌렸다.** 잠금 순서가 맞는지는 함수 본문으로 확인하고
  (마이그레이션 시험), 흐름은 한 연결에서 순서대로 확인한다. 개발 기계에 진짜 Postgres 가 없어
  (PGlite 는 연결이 하나다) 정답표 저장과 사진 올리기를 진짜로 겹쳐 보지는 못했다.
- 학생은 사진에서 읽힌 자기 답을 볼 수 없다. 흐린 사진만 알려 준다.
- 모집 페이지(`/class`)와 무료 접수(`/apply`)의 문구는 아직 국어 기준이다.

## 시트를 빼기로 한 이유 (BE-4 제외)

PRD 는 Supabase(원본) → Google Sheets(사람이 보기 쉬운 사본) → Notion(운영판) 세 갈래였다.
그런데 시트가 맡기로 했던 일이 대부분 다른 곳으로 옮겨갔다.

- `_설정` 탭(접수 on/off·상한·과목 차단) → Supabase `app_settings` 로 이동, 이미 동작 중
- `_실패` 탭(오류 로그) → `submissions.status` + `sheet_ok`/`notion_ok` 로 대체 (워커 작업 때 `sync_failures` 로 정리)
- `접수` 탭 → Notion 과 같은 데이터의 사본

남는 건 사본 하나인데, 그 대가로 구글 클라우드 프로젝트·서비스 계정·JSON 키·시트 공유라는 수동 단계와
비밀 키 하나가 늘어난다. 접수 10~30건 규모에서 시트가 주는 이득(피벗 집계)은 Notion 뷰로 충분히 대신된다.

2026-08-28 사용자 결정으로 **v1 에서 제외**한다. `submissions.sheet_ok` 컬럼은 남겨 둔다 — 나중에 붙일 때
스키마를 다시 건드리지 않기 위해서다. 집계가 필요하면 Supabase Table Editor 의 CSV 내보내기를 쓴다.

G4(자동 반영 성공률)는 Notion 단독 기준으로 읽는다.

## 접수 뒤에 일어나는 일

```
학생 제출 → /api/submit → 접수번호 즉시 반환 (학생 화면은 여기서 끝)
                        ↓ after() — 응답을 보낸 뒤 같은 함수 안에서 이어서
              과목별 사진 → PDF 한 개로 병합 → Storage 저장
              과목별 Notion 페이지 생성 (시험지 PDF 는 만료 있는 서명 URL)
              접수 확인 메일 발송
                        ↓
              전부 성공하면 status = 'synced', 하나라도 실패하면 'failed' + sync_failures 기록
```

- **단계마다 따로 실패를 받는다.** PDF 가 실패해도 Notion 등록과 메일은 나간다.
- **여러 번 돌려도 결과가 같다.** 이미 만든 PDF·Notion 페이지·보낸 메일은 건너뛴다.
- **튜터에게 줄 PDF 링크까지가 성공이다.** PDF 를 만들었어도 Notion 에 넣을 서명 링크를 못 만들면 실패로 적고
  다음 판이 링크를 채운다 — 링크 없는 페이지를 완료로 치지 않는다.
- **실패한 접수는 곧바로 다시 집지 않는다**(0018). 마지막으로 집은 지 10분이 지나야 다시 집으므로, 크론 한 판에
  한 번씩 닷새에 걸쳐 다시 해 본다. 예전에는 빨리 실패하는 접수 하나가 한 판 안에서 재시도 다섯 번을 다 썼다.
- **막힌 접수 되살리기**: `POST /api/worker/process` 를 부르면 밀린 것부터 최대 5건을 다시 처리한다.
  특정 건만 하려면 `?receipt=F0902-013`. `WORKER_SECRET` 을 `x-worker-secret` 헤더(또는 `Authorization: Bearer`)로
  보내야 한다 — 열쇠를 안 넣은 배포에서는 이 주소가 아예 안 열린다.
- `/setup` 이 밀린 건수와 해결 안 된 오류 건수를 같이 보여준다.

## 알아 둘 것

- **초안 경로**: 제출 전에는 접수번호가 없어서 이미지를 `raw/drafts/{draftId}/{과목}/{순번}.jpg` 에 쌓는다.
  PRD 의 `raw/{접수번호}/...` 로 묶는 일은 제출(BE-2) 때 한다.
- **새로고침 후 재시도**: 실패한 장의 원본 blob 은 메모리에만 있다. 새로고침하면 그 장은 다시 고르라고 안내한다.
- **Vercel Web Analytics**: 단계마다 주소가 달라서 페이지뷰만으로 퍼널이 그려진다
  (`/` → `/apply/exam` → `/apply/upload` → `/apply/concerns/[과목]` → `/apply/email` → `/done`).
  완료 화면 주소의 접수번호는 `src/components/Analytics.tsx` 의 `beforeSend` 에서 잘라내고 보낸다.
- **PDF 파일명은 영문이다.** PRD BE-3 은 `{접수번호}_{학년}_{과목}.pdf` 를 한글로 적었지만,
  스토리지 키에 한글을 넣으면 `Invalid key` 로 거부당하고, 다운로드 파일명 파라미터도 서버가
  디코드하지 않아 `%25EA%25B3%25A0…` 로 이중 인코딩된다. `F0902-013_G3_math.pdf` 형태로 간다.
- **막힌 접수 되살리기**: `POST /api/worker/process?receipt=F0902-013` (헤더 `x-worker-secret`).
  사람이 집어서 부르는 것이므로 자동 재시도 한도에 걸려 있어도 풀고 다시 돌린다.
  무엇이 왜 막혔는지는 `GET /api/worker/status` — `?probe=1` 은 저장소에서 사진을 실제로 받아보고,
  `?mail=1` 은 운영자 주소로 시험 메일을 보내본다.
- **장수 상한은 과목마다 다르다.** 기본 12장이고 국어만 16장이다 — 학생 문제지가 실제로 16장이라
  12장으로는 시험지를 다 못 올린다. 숫자는 `config/app.ts` 의 `maxPhotosBySubject` 한 곳에 있고,
  화면·서버·안내 문구가 모두 `maxPhotosFor()` 하나만 본다. 한쪽만 고쳐서 화면은 받아주는데
  서버가 거절하는 사고를 막기 위해서다. 다른 과목도 장수가 다르면 그 표에 한 줄 더하면 된다.
  전체 상한 40장은 그대로다 — 국어 16 + 다른 과목 12 + 12 = 40 이라 세 과목까지는 들어간다.
- **사진 저장 경로는 사진 고유 id 를 쓴다** (`raw/drafts/{초안}/{과목}/{사진id}.jpg`).
  순번을 쓰면 사진을 지웠다 다시 올릴 때 같은 번호가 다시 나와 먼저 올린 파일을 덮어쓴다.
  순서는 제출할 때 `order_index` 로 따로 보낸다.
- **제출 시 경로를 검증한다.** 모든 사진 경로가 그 접수의 초안 id·과목과 맞는지 확인하고,
  같은 경로가 두 번 오면 거절한다. 남의 접수 사진을 끼워 넣거나 같은 장이 PDF 에 두 번 들어가지 않게 한다.
- **하루 한 번 정리**: `vercel.json` 의 크론이 매일 03:00(KST) `/api/worker/cron` 을 부른다.
  ① 밀린 접수 처리 — 제출 직후 후처리가 시간 초과로 잘린 건을 되살린다. 이게 없으면 아무도 다시 돌려주지 않는다.
  ② 보관 기간이 지난 사진·PDF 삭제. `purge_after` 가 지난 접수의 파일을 지우고 `status = 'purged'` 로 표시한다.
  접수 기록 자체는 남긴다 — 몇 건 받았고 언제 회신했는지는 계속 봐야 하기 때문이다.
  ③ 주인 없는 사진 삭제 (24시간 지난 것만).
  ④ 90일 지난 수업 신청 삭제. ⑤ 성적 관리의 사진 읽기 되살리기 — 멈췄거나 요청 몰림 · 서버 오류로
  실패한 읽기를 한 번 더 돌린다(0016). 그래서 이 크론은 300초까지 돈다.
  **`CRON_SECRET` 을 `WORKER_SECRET` 과 같은 값으로 넣어야 자동으로 돈다.**
- **며칠 뒤 이어하기로 돌아온 제출은 사진이 있는지부터 본다.** 초안 사진은 하루 뒤 크론이 지우므로, 제출 API 가
  저장소에 파일이 실제로 있는지 확인하고 없으면 `UPLOAD_EXPIRED` 로 그 사진만 돌려준다. 화면은 그 사진을
  '안 올라감' 으로 돌리고 다시 고르게 한다 — 고민과 이메일은 그대로다. 예전에는 접수번호가 나간 뒤 PDF 를
  영영 못 만들었다. 크론도 지우기 직전에 참조 목록을 한 번 더 읽는다.
- **주인 없는 사진이 저장소를 갉아먹는다.** 사진은 ②단계에서 곧바로 저장소로 올라가지만
  접수 기록은 ④단계를 끝내야 생긴다. 중간에 창을 닫으면 사진만 남고 접수는 없다.
  보관 기간 정리는 접수 기록을 따라가므로 이 파일들을 영영 못 잡는다. 무료 용량이 1GB 라
  쌓이는 만큼 받을 수 있는 학생이 줄어든다. 그래서 크론이 매일 따로 훑는다.
  지금 무엇이 얼마나 쌓였는지는 `GET /api/worker/storage`.
  손으로 치우려면 `POST /api/worker/storage?mode=orphans` (24시간 지난 것),
  `&hours=0` 이면 방금 올라온 것까지 — **접수를 열기 전에만 쓴다.**
  `&dry=1` 은 지우지 않고 개수만 센다.
- **접수 1건 통째로 지우기**: `POST /api/worker/purge?receipt=F0902-013&mode=delete`.
  사진·PDF·DB 기록·Notion 페이지까지 지운다. 되돌릴 수 없다.
- **버킷 통째로 비우기**: `POST /api/worker/storage?mode=wipe&confirm=WIPE-ALL`.
  접수에 걸려 있는 사진까지 전부 지운다. 실수로 부를 수 없게 확인 문구를 받는다.
- **고민 답변은 Notion 페이지 본문에 들어간다.** 속성 칸에 합쳐 넣으면 2000자 제한에 걸리고
  표에서 읽히지도 않는다. 속성 `고민` 은 목록에서 훑을 한 줄 요약(답변 개수 · 어려운 문항 · 원하는 피드백 ·
  첫 답변 앞부분)이고, 문답 전문은 본문에 문항별 제목과 문단으로 들어간다.
- **접수 스위치(OPS-1)** 는 Supabase `app_settings` 를 읽는다. 브라우저에서 세션당 한 번 읽으므로,
  스위치를 바꾼 뒤에는 새로고침해야 반영된다. 제출 API 는 매번 서버에서 다시 확인한다.
- **제출 멱등성**: 클라이언트가 만든 멱등키가 `submissions.idempotency_key` 에 유니크로 들어간다.
  같은 제출을 여러 번 눌러도 접수는 1건이고, 같은 접수번호가 돌아온다.
- **비밀값**: `SUPABASE_SERVICE_ROLE_KEY` 는 서버에서만 쓴다(`src/lib/supabase/admin.ts` 는 `server-only`).
  절대 `NEXT_PUBLIC_` 접두사를 붙이지 말 것 — 붙이면 브라우저로 새어 나가 DB 전체가 열린다.
- **저장소를 막아 둔 브라우저**: 사파리 프라이빗 모드나 '사이트 데이터 차단' 을 켜면
  `localStorage` 의 메서드가 예외를 던진다. 그러면 이어하기를 위한 복원이 끝나지 않아
  접수 화면이 "불러오는 중…" 에서 영영 멈춘다 — 터지지도 않아 학생은 느린 줄만 안다.
  `store.ts` 의 `safeStorage` 가 메모리로 받아내서 접수는 끝까지 되게 한다(새로고침 이어하기만 잃는다).
  같은 이유로 초안 id 도 한 번 만든 값을 붙잡아 둔다 — 부를 때마다 새로 만들면 사진마다
  다른 폴더에 올라가고 제출이 통째로 거절된다.
- **날짜는 전부 한국 시간**: 서버는 UTC 로 돌고 DB 함수는 `at time zone 'Asia/Seoul'` 로 적혀 있다.
  회신 예정일·삭제 예정일·접수번호의 MMDD 를 서버에서 UTC 로 세면 새벽 0~9시에 하루가 어긋난다.
  `src/lib/kst.ts` 하나만 쓴다.
- **조회 실패와 '없음' 은 다른 말**: `listClasses()` 는 `{ rows, failed }` 를 준다. 오류일 때 빈 배열을
  주면 모집 페이지가 "지금은 열린 반이 없어요" 로 바뀌어, 그날 찾아온 사람을 전부 놓친다.
- **원점수는 적는 화면에서 막는다**: 만점을 넘겨도 그냥 두면 제출 순간에 서버가 거절하는데,
  그때는 이미 다른 화면이라 어느 과목의 무엇이 잘못됐는지 알 수 없다. `scoreProblem()` 이
  화면과 서버 양쪽에서 같은 기준을 본다.
- **관리자 서버 함수는 예외 대신 로그인 화면으로**: 7일이 지나 쿠키가 만료된 것뿐인데 예외를
  던지면 "잠시 문제가 생겼어요" 라는 알 수 없는 화면이 뜬다. 어느 쪽이든 그 함수는 실행되지 않는다.
- **운영용 주소는 열쇠가 없으면 무조건 막힌다**(`lib/worker-auth.ts`). 예전에는 재처리 주소 하나가
  `WORKER_SECRET` 을 안 넣은 배포에서 누구나 부를 수 있었다. 잠금은 기본값이어야 한다.
