학생이 스크롤하는 순서가 곧 설득의 순서다. 무엇을 하는 수업인지 → 누구와 하는 수업인지 → 지금 어느 반이 열려 있는지. 이 셋 말고는 넣지 않는다.

성공 기준

  • 2주 안에 3인 반 두 개(6명). 20명 중 6명이면 30%, 매출 2,988,000원.
  • 메일 → 페이지 → 신청 폼 제출 15% 이상. 모수가 20명뿐이라 비율보다 절대수를 본다.
  • 신청자 중 “관찰이 불편하다”는 이유의 이탈 0명. 걸러내는 것도 이 페이지의 일이다.

하지 않는 것

  • 온라인 결제 — 신청 뒤 카카오톡으로 안내한다. 6명 받자고 PG 를 붙이지 않는다.
  • 학생 로그인·마이페이지 — 신청은 폼 한 번으로 끝난다.
  • 출결·성적 관리 — 수업 운영 도구는 이 페이지의 범위가 아니다.
  • 국어 외 과목 — 수학은 100분이라 180분 구조에 들어가지 않는다.

03 — 섹션 ②

우리는 이런 학생을 원해요

거르는 문장을 페이지에 그대로 쓴다. 3인 정원이라 한 명을 잘못 받으면 세 명의 수업이 흔들리고, “관찰당하는 게 불편한 학생”은 우리가 가장 잘 못 가르치는 학생이다.

이런 학생과 합니다
  • 다른 사람이 푸는 걸 옆에서 보면 자극을 받는 학생
  • 아는데 시간이 모자라서 틀리는 학생
  • 자기 습관을 지적받을 준비가 된 학생
  • 혼자 풀 때와 시험장에서의 자기가 다르다고 느끼는 학생
이런 학생은 다른 곳이 낫습니다
  • 개념이 아직 안 잡힌 학생 — 80분을 채우지 못하면 관찰할 것이 없습니다
  • 전 문항 해설을 원하는 학생 — 해설은 90분 중 30분뿐입니다
  • 옆에서 지켜보는 것이 불편한 학생
“학생의 행동을 관찰해서, 나아지게 하는 수업.”

페이지에서 이 문장은 한 번만, 이 자리에서만 쓴다. 반복하면 표어가 되고 표어는 읽히지 않는다.

04 — 섹션 ③ · 데이터

현재 개설되어 있는 클래스

반 이름·요일·시작일·회차·튜터는 반마다 다르고 계속 바뀐다. 그래서 이 구간만 DB 에서 읽고 /admin 에서 고친다. 나머지 페이지는 코드에 박아 둔다 — 바뀌지 않는 것을 편집 가능하게 만드는 것이 관리 비용이다.

수강료는 지금 모든 반이 498,000원이지만 컬럼으로 둔다. 반마다 회차가 다르게 열릴 수 있고, 그때 코드를 고치러 오는 것이 관리자 페이지를 만드는 이유를 무너뜨린다. 1회당 금액(price ÷ sessions)은 화면에서 계산해 같이 보여준다.

표 하나를 더한다

-- supabase/migrations/0005_classes.sql create table if not exists classes ( id uuid primary key default gen_random_uuid(), slug text unique not null, -- korean-thu-19 subject_code text not null default 'korean', title text not null, schedule_text text not null, starts_on date, sessions int not null default 4, location text not null, tutor_name text not null, tutor_school text, tutor_percentile numeric(4,1), proof_paths text[] not null default '{}', -- tutor-proof 버킷 경로 recommend text, detail text, capacity int not null default 3, price int not null default 498000, price_note text not null default '4회 총액 · 모의고사 4회분, 스터디룸, 수업 후 피드백 포함', status text not null default 'draft', -- draft|open|closed sort_order int not null default 0, updated_at timestamptz not null default now() ); -- 익명 정책을 만들지 않는다 = 브라우저에서 직접 못 읽는다. -- 페이지는 서버 컴포넌트가 service_role 로 읽어서 그린다 -- (app_settings · exam-papers 와 같은 방침). alter table classes enable row level security;

증빙 자료

  • 새 비공개 버킷 tutor-proof. 기존 exam-papers 와 섞지 않는다 — 보관 규칙이 다르다(학생 사진은 30일 뒤 삭제, 증빙은 남는다).
  • 페이지는 서버에서 짧은 유효기간의 서명 URL 을 만들어 <img> 에 넣는다. 공개 버킷으로 열지 않는다 — 주소가 한 번 새면 계속 열려 있다.
  • 올리기 전에 가린다. 성적표에는 이름·수험번호·생년월일이 같이 찍혀 있다. 관리자 화면 업로드 칸 옆에 이 문장을 띄우고, 가린 이미지만 올린다.
기존 규칙 그대로. SUPABASE_SERVICE_ROLE_KEY 는 서버에서만 쓰고 NEXT_PUBLIC_ 접두사를 붙이지 않는다. 클래스 목록은 /class 서버 컴포넌트가 supabaseAdmin() 로 읽고 dynamic = 'force-dynamic' 으로 캐시하지 않는다 — 관리자에서 고친 값이 바로 보여야 한다.

빈 상태와 마감 상태

  • 모집중인 반이 없을 때 — “지금은 열린 반이 없어요. 다음 반이 열리면 알려드릴게요” + 알림 신청(연락처 한 칸). 페이지를 빈 채로 두지 않는다.
  • 정원이 찼을 때 — 카드는 남기고 버튼만 “대기 신청”으로. 찬 반이 보이는 것 자체가 근거다.
  • 초안(draft) — 페이지에 나오지 않는다. /class?preview=<토큰> 로만 확인한다.

  • /admin 아래 모든 경로와 쓰기 API 를 같은 검사로 막는다. 화면만 막고 API 가 열려 있으면 잠근 것이 아니다.
  • 쓰기는 전부 서버에서 supabaseAdmin() 으로. 브라우저는 Supabase 를 직접 만지지 않는다.
  • 같이 처리한다 — 지금 /setup 은 아무나 열 수 있고 접수 건수와 환경변수 상태가 보인다. 같은 잠금 뒤로 옮긴다.
구현 전에 확인. 이 저장소는 Next 16 이고 훈련 데이터의 Next 와 다르다(AGENTS.md). 미들웨어 · 쿠키 · 서버 액션의 호출 형태는 node_modules/next/dist/docs/ 를 읽고 쓴다. 이 문서는 “무엇을 막는가”까지만 정한다.
06 — 신청

신청은 네 칸, 결제는 카톡으로

카드의 신청 버튼을 누르면 그 반이 선택된 채로 폼이 열린다. 학생이 채우는 칸은 넷뿐이다 — 더 물어보면 여기서 떨어져 나간다. 나머지는 접수번호 하나로 9모 접수에서 끌어온다.

칸예시왜 이것만
학생 이름김○○반 편성 · 카톡에서 부를 이름
9모 피드백 접수번호F0902-013이 번호 하나에 학년 · 과목 · 그때 적어준 고민 · 시험지가 다 딸려 온다
학부모 연락처010-0000-0000자리 확정과 입금 안내를 여기로 보낸다
개인정보 동의체크 한 번수집 항목 세 가지와 90일 보관을 그 자리에서 보여준다

희망 반은 학생이 고르는 칸이 아니다 — 눌러 온 카드에서 따라온다 (/class/[slug]/apply). 학년 · 이메일 · 고민은 묻지 않고 접수번호로 조회한다.

접수번호를 못 찾을 때

  • 칸 아래 안내 한 줄 — “접수 확인 메일에 있는 F 로 시작하는 번호예요. 예: F0902-013”
  • 번호가 틀려도 신청은 받는다. 대조에 실패했다고 막지 않는다 — 신청을 놓치는 쪽이 더 나쁘다. 관리자 목록에 ‘대조 실패’ 로만 표시하고 사람이 확인한다.

누르고 나면

  • 완료 화면 — “남겨주신 번호로 카카오톡 드릴게요. 자리와 입금은 그때 안내합니다.” 계좌번호는 페이지에 올리지 않는다.
  • 같은 순간 팀 메일로 알림. 기존 src/lib/email.ts 를 그대로 쓴다.
  • 정원 초과는 서버에서 한 번 더 막는다. 화면에서만 막으면 동시에 눌린 두 명이 다 통과한다 — create_submission 에서 이미 겪은 문제다.
  • 상태는 관리자 화면에서 사람이 옮긴다 — 신청 → 연락함 → 입금 완료.
  • 환불 기준은 페이지에 넣지 않는다(결정). 입금 전 카톡 단계에서 정리한다.
-- supabase/migrations/0006_class_applications.sql create table if not exists class_applications ( id uuid primary key default gen_random_uuid(), class_id uuid not null references classes(id) on delete restrict, student_name text not null, receipt_no text, -- F0902-013 · 9모 접수번호 parent_phone text not null, consent_at timestamptz not null, status text not null default 'new', -- new|contacted|paid|canceled memo text, purge_after date not null, -- 신청일 + 90일 created_at timestamptz not null default now() ); -- 익명 정책 없음. 쓰기는 서버가 service_role 로만 한다. -- 90일 삭제는 기존 purge 크론에 한 줄 더 얹는다 (사진과 달리 행 자체를 지운다). alter table class_applications enable row level security; create index if not exists class_applications_class_idx on class_applications (class_id, created_at desc);
07 — 발송

20명에게 Gmail 로 직접 보낸다

자동 발송을 붙이지 않는다. 20명이면 손으로 보내는 편이 빠르고, 무엇보다 한 사람마다 그 학생 피드백에서 나온 문장 한 줄을 넣을 수 있다. 그 한 줄이 이 메일의 전부다.

받는이 학생 1명 (개별 발송)
제목 9월 시험지 피드백, 그 다음 이야기 — 국어 3인 관찰반을 엽니다
{이름} 학생, 지난달에 9월 모의고사 시험지 보내주셨던 팀과외팀입니다. 그때 {이름} 학생 시험지에서 {그 학생 피드백의 한 문장} 이라고 적어 보냈었죠. 그런데 시험지 사진으로는 거기까지가 한계였습니다. 어떤 순서로 풀었는지, 어디서 몇 분을 썼는지는 사진에 남지 않으니까요. 그래서 시험을 치는 중에 옆에 앉아 보기로 했습니다. 180분 동안 실전 모의고사 80분을 그대로 치고, 튜터가 옆에서 지문별 시간과 오래 걸린 문항을 기록합니다. 쉬고 나서 남은 90분에 그 기록을 놓고 이야기합니다. 3명 정원입니다. 수업이 어떻게 굴러가는지, 지금 어떤 반이 열려 있는지 여기에 정리해 뒀습니다. https://…/class?from=mail 읽어보시고 맞지 않다 싶으면 답장 안 주셔도 괜찮습니다. 궁금한 건 이 메일에 그대로 답장 주세요. 팀과외팀 드림
  • 참조·숨은참조로 묶어 보내지 않는다. 20명을 한 통에 넣으면 서로의 메일 주소가 보인다. 개별 발송이거나, 최소한 BCC 다.
  • 링크는 ?from=mail 을 달아 보낸다. 이미 붙어 있는 Vercel Web Analytics 로 도달 수를 센다 — 메일 열람은 추적하지 않는다.
  • 보내는 시각은 평일 저녁. 학생이 직접 읽는 계정이다.
  • 답장이 오면 사람이 답한다. 이 메일은 자동화 대상이 아니다.

09 — 순서

만드는 순서

M1 만으로도 20명에게 메일을 보낼 수 있다. 반이 하나뿐이면 표가 없어도 되고, 표가 없으면 하루가 줄어든다.

  • M1 · 반나절 — /class 정적 페이지. 섹션 ①②까지, 클래스는 코드에 박아 둔 한 개. CTA 는 문의 메일. 여기까지 하고 메일을 보낸다.
  • M2 · 하루 — classes 표 + 서버 렌더. 빈 상태 · 마감 상태 포함.
  • M3 · 하루 — /admin 잠금과 편집 폼, 증빙 업로드. /setup 도 같이 잠근다.
  • M4 · 하루 — 신청 폼 · 알림 메일 · 신청자 목록 · 입금 표시 · 90일 삭제.
10 — 착수

막는 것은 없다

미결이 다 닫혔다. 아직 안 정해진 값은 전부 /admin 에서 넣는 것들이라 M1 을 지금 시작할 수 있다.
