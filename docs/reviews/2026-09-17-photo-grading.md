# Claude 전달용 코드 리뷰 및 수정 요청

리뷰 날짜: 2026-09-17

범위: 현재 작업 트리의 미커밋 변경과 새 파일. 사진 OCR 자동 채점, 관련 SQL 마이그레이션, 학생·튜터 화면, 재시도 작업을 중심으로 검토했다. 아래 줄 번호는 리뷰 시점 기준이다. 애플리케이션 소스는 수정하지 않았다.

## 1. [P1] 사진이 바뀌면 이전 자동 채점을 무효화해야 한다

위치: `supabase/migrations/0016_lms_photo_grading.sql:175–188`, `:247–263`, `:96–101`

`request_photo_read`는 상태와 요청 번호만 바꾸고 기존 `lms_answers`는 남긴다. 실행 상한에 걸리면 요청 번호도 바꾸지 않고 반환한다. 따라서 사진을 바꾼 뒤 새 읽기가 진행 중이거나 실패하거나 상한에 걸려도 이전 사진으로 만든 채점이 완료 상태로 남는다. `publishGradedAttempts`는 채점 문항 수만 확인하므로 이 점수를 공개할 수 있다. 공개되고 나면 새 OCR 결과는 적용되지 않는다.

또한 `finish_photo_read`는 요청 번호만 확인하고 현재 사진 집합과 입력 `photo_ids`의 일치를 확인하지 않는다. 마지막 허용 실행 도중 사진이 바뀌고 추가 요청이 상한으로 거절되면, 이전 사진의 결과가 최신 요청으로 인정되어 저장된다. `apply_photo_read_locked` 역시 현재 사진을 검사하지 않아 오래된 완료 결과를 다시 적용할 수 있다.

재현 조건:

1. 사진으로 30문항이 모두 채점된 비공개 응시를 준비한다.
2. 학생이 사진을 교체하거나 삭제한다.
3. 새 읽기를 지연·실패시키거나 `runs = 8`로 상한에 걸리게 한다.
4. 이전 채점이 그대로 남고 일괄 공개 대상에 포함되는지 확인한다. 모든 사진을 지워도 같은 문제가 생긴다.

수정 방향:

- 사진 변경과 결과 무효화를 하나의 DB 트랜잭션으로 처리한다. 모델 호출 상한과 무효화는 분리한다.
- 사진 버전 또는 사진 ID 집합을 저장·적용 시 검증하고, 오래된 결과는 거부한다. 트랜잭션 밖에서 한 번 비교하는 것만으로는 동시 변경을 막지 못한다.
- 오래된 자동 채점은 지우거나 명시적인 무효 상태로 두고, 일괄 공개·PDF 점수 생성 경로에서도 제외한다. 튜터가 직접 저장한 채점은 보존한다.
- 사진이 0장이면 모델 호출 없이 자동 채점을 정리한다.

검증: 읽는 중 사진 교체, 완료 후 교체, 마지막 사진 삭제, 상한 도달, 읽기 실패를 각각 시험한다. 오래된 결과 저장·재적용·공개가 거부되고 튜터 채점은 보존되어야 한다.

## 2. [P1] SDK 재시도가 전체 OCR 시간 예산을 초과한다

위치: `src/lib/lms/ocr.ts:340`

`timeout`에 남은 시간을 넣어도 `maxRetries: 2`이면 같은 제한이 매 시도에 다시 적용된다. 설치된 SDK의 `client.mjs`에서 재시도가 같은 options를 사용함을 확인했다. 180초 타임아웃이 반복되면 최대 3회 시도와 재시도 대기 시간이 발생하므로, 230초 작업 예산과 300초 서버 함수 제한을 넘을 수 있다. 서버가 먼저 종료되면 `fail_photo_read`를 호출하지 못하고 상태가 `running`으로 남는다. 크론의 `deadline`도 같은 이유로 보장되지 않는다.

로컬 검증: 외부 요청 없이 SDK의 fetch를 모킹했다. `timeout: 40`, `maxRetries: 2`에서 실제로 3회 호출했고 약 142ms 뒤 실패했다. 전체 40ms 제한으로 동작하지 않는다.

수정 방향:

- SDK 자동 재시도를 끄고, 각 시도·대기 전에 절대 deadline을 확인하는 재시도 루프를 구현한다.
- 전체 작업에 AbortController를 연결해 실행 중인 요청도 종료할 수 있게 한다. 실패 기록에 필요한 시간을 남긴다.
- deadline에 의한 중단은 `TIMEOUT`으로 기록하고, 사진 다운로드와 여러 배치의 합계도 같은 예산을 사용한다.

검증: 연속 타임아웃 및 429/503과 긴 Retry-After를 모킹한다. 전체 deadline 이후 추가 호출이 없어야 하며, 서버 제한 전에 실패 상태가 기록되어야 한다.

## 3. [P2] 폴링이 멈춤 판정보다 먼저 종료되어 복구 버튼이 나오지 않는다

위치: `src/components/lms/useReadWatch.ts:30–35`

클라이언트는 8분 후 폴링을 끝내지만 서버의 `PHOTO_READ.stuckMs`는 10분이다. 읽기 시작 무렵부터 화면을 열어 두고 서버 작업이 중단되면, 마지막 상태 조회까지 계속 `reading`이다. 8분에 `active`만 false로 바뀌고 refresh나 오류 표시가 없으므로 `PhotoReadPanel`은 읽는 중 화면에 남는다. `stuck` 상태에서 제공하는 다시 읽기 버튼도 사용자가 직접 새로고침하기 전까지 나오지 않는다.

로컬 검증: 고정 시각으로 `readViewOf`를 호출해 8분 4초에는 `reading`, 10분 초과에는 `stuck`임을 확인했다.

수정 방향:

- 서버의 멈춤 기준 이후까지 관찰하거나, 폴링 종료 시 명시적인 시간 초과 상태와 복구 동작을 제공한다.
- 새 요청을 감시할 때 타이머를 재시작할 수 있도록 요청 번호를 기준으로 감시 수명을 관리한다.
- 저장하지 않은 채점이 있으면 입력을 보존하면서 복구 안내를 보여 준다.

검증: 가짜 시계로 시작 직후부터 11분까지 진행하고, 중단된 작업에 대해 복구 UI가 노출되는지 확인한다. 폴링 중 새 요청이 시작되는 경우도 확인한다.

## 4. [P2] 크론 재시도 대상의 횟수 필터를 LIMIT 전에 적용해야 한다

위치: `src/lib/lms/photo-read.ts:235` 및 앞의 failed/stuck 조회

DB에서 오래된 행을 `limit(opts.limit)`개 가져온 뒤 JavaScript에서 `runs < maxRetryRuns`를 검사한다. 예를 들어 오래된 실패 5개가 모두 12회 상한에 도달했으면, 그 뒤에 재시도 가능한 실패가 있어도 `limit: 5` 조회 결과에는 들어오지 않는다. 실제로 처리할 수 있는 작업이 있는데 크론이 0건으로 끝나고, 다음 날에도 같은 행에 가로막힐 수 있다.

수정 방향: failed와 stuck 양쪽 DB 조회에 `.lt('runs', PHOTO_READ.maxRetryRuns)`를 `limit` 전에 적용한다. 두 조회 결과를 합칠 때도 처리 순서를 명확히 한다.

검증: 상한에 도달한 오래된 행 5개와 재시도 가능한 최신 행 1개를 준비한다. `limit: 5` 실행에서 최신 행이 처리 대상에 포함되어야 한다.

## 검증 결과 및 제한

- `npm run typecheck`: 통과.

- SQL 관련 판단은 정적 검토다. DB 통합 테스트와 실제 브라우저·Claude API 호출은 실행하지 않았다. `test:db`는 연결된 테스트 DB의 LMS 데이터와 파일을 비우므로 전용 폐기 가능한 DB에서만 실행해야 한다.
