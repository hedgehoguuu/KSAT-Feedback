## 1. [P1] 오래된 채점 폼이 무효화된 사진 점수를 다시 저장·공개한다

위치: `supabase/migrations/0016_lms_photo_grading.sql:427–452`

관련 경로: `src/components/lms/GradeSheet.tsx`, `src/app/lms/course-actions.ts:233–260`, `src/components/lms/PhotoReadPanel.tsx:89–95`

사진 변경 트리거가 이전 자동 채점을 지우고 일괄 공개 RPC가 이를 재검사하지만, 개별 채점 저장에는 화면이 읽었던 버전 검사가 없다. `save_grading`은 응시 행을 잠근 다음 전달된 답안을 그대로 다시 넣고 `answers_source = 'tutor'`로 바꾼다. 서버 액션이 응시를 다시 조회해도 제출된 답안이 어느 사진·채점 버전에서 왔는지 확인하지 않는다.

따라서 사진 변경 전 열어 둔 폼으로 이전 자동 채점을 복원하고 공개할 수 있다. 사진 읽기가 이미 완료된 화면에는 `ReadWatcher`도 마운트되지 않아 이후 학생의 변경을 감지하지 못한다. 튜터 채점 또는 공개 상태가 되면 새 OCR 결과도 이를 고치지 않는다.

재현 순서:

1. 사진 OCR로 채점이 완료된 비공개 응시를 튜터 화면에서 연다.
2. 학생이 사진을 교체한다. 트리거가 기존 자동 채점을 지운다. 새 OCR은 지연시키거나 실패시킨다.
3. 튜터가 열어 둔 화면에서 별도 수정 없이 ‘저장하고 점수 공개’를 누른다.
4. 이전 사진의 답안이 다시 저장되고 `tutor / published`가 된다. 일괄 공개의 최신성 검사는 이 경로에 적용되지 않는다.

수정 제안:

- 폼이 읽은 채점 버전(예: 명시적인 grading revision)을 hidden 필드 → 서버 액션 → `saveGrading` → RPC로 전달한다.
- RPC가 응시 행을 잠근 후 버전을 비교하고, 불일치하면 삭제·삽입·공개 전에 충돌로 반환한다. 서버 액션에서 최신 버전을 조회해 대신 전달하면 보호가 되지 않는다.
- 자동 채점의 무효화·재적용 및 튜터 저장 시 버전을 갱신한다. 충돌 시 입력을 보존하고 최신 사진·채점 확인을 안내한다.
- 이미 저장된 튜터 채점을 사진 변경으로 지우지 않는 기존 정책은 유지한다.

회귀 검증: 위 순서를 DB 통합 테스트와 두 브라우저 세션으로 재현한다. 오래된 폼의 ‘저장만 하기’와 ‘저장하고 점수 공개’ 모두 충돌해야 하고, 최신 버전을 확인한 저장은 성공해야 한다.

근거 수준: 폼·서버 액션·RPC의 정적 경로 검토. 실제 DB·브라우저 재현은 미실행이다.

## 2. [P2] 정답표 저장과 사진 변경의 잠금 순서가 반대여서 교착될 수 있다

위치: `supabase/migrations/0016_lms_photo_grading.sql:514–535`

관련 경로: 같은 파일의 `lms_photos_changed`, `:102–115`

`save_answer_key`는 먼저 `lms_answers`를 UPDATE해 답안 행 잠금을 잡고, 이어지는 자동 채점 재적용 루프에서 `lms_attempts`를 잠근다. 반면 사진 변경 트리거는 응시 행을 먼저 잠그고 답안 행을 DELETE한다. 파일 머리말의 설명과 달리 답안과 응시를 역순으로 잠근다.

가능한 실행 순서:

1. 자동 채점이 완료된 비공개 응시가 있다. `photo_reads.status = 'done'`, `answers_source = 'photo'`이고 학생 답이 저장되어 있다.
2. 트랜잭션 A가 정답표를 바꾸고 `:515`에서 해당 답안 행을 UPDATE한다.
3. 트랜잭션 B가 사진을 추가한다. 트리거가 응시 행을 잠그고, 답안 DELETE에서 A의 잠금 해제를 기다린다.
4. A가 `:535`에서 같은 응시 행을 잠그려다 B를 기다린다.
5. DB가 교착을 감지하면 한쪽 트랜잭션을 중단한다. 정답표 저장 또는 사진 저장이 실패한다.

수정 제안:

- 정답표 저장에서 답안 행을 변경하기 전에 영향을 받는 응시 행들을 일정한 ID 순서로 잠근다. 이후 정답표 갱신·재채점·OCR 재적용을 처리한다.
- `finish_photo_read`, `apply_photo_read`, 사진 변경 트리거, 튜터 저장까지 응시·답안 잠금 순서를 함께 검토한다. 일부 경로에만 회차 잠금을 추가하는 것으로 끝내지 않는다.
- 재시도만 추가해 잠금 순서 문제를 가리지 않는다.

회귀 검증: 전용 DB의 두 연결에서 동기화 지점을 두어 위 순서를 강제로 겹친다. 정답표 저장과 사진 추가가 모두 성공하고, 바뀐 사진의 이전 자동 채점이 남지 않는지 확인한다. 기존 DB 테스트는 이 부분을 순차 실행하므로 교착을 검증하지 않는다.

근거 수준: SQL 잠금 획득 순서의 정적 검토. 실제 동시 트랜잭션 재현은 미실행이다.

## 3. [P2] 반별 목록에서 첫 OCR의 진행·실패·멈춤 상태가 사라진다

위치: `src/app/lms/exams/[id]/page.tsx:291–292`

`StudentLine`이 실제 현재 사진 대신 `read.photo_ids`를 `readViewOf`의 현재 사진 목록으로 전달한다. 그런데 `photo_ids`는 완료한 읽기의 사진 목록이다. 첫 요청을 기다리거나 처리 중이거나 첫 요청이 실패했다면 기본값 `[]` 그대로다. `readViewOf`는 사진 목록이 비어 있으면 상태 검사 전에 `none`을 반환한다. 실제 사진이 있어도 목록에는 ‘시작 전’만 표시되고 실패·멈춤 표시가 누락된다. 모든 사진 삭제 후 다시 업로드하는 경우에도 같은 문제가 생긴다.

외부 API 없이 실제 상태 함수로 확인한 결과:

| 읽기 상태 | 실제 사진 ID를 전달 | 현재 반별 목록 호출 |
| --- | --- | --- |
| pending | reading | none |
| running | reading | none |
| failed | failed | none |
| 11분 지난 running | stuck | none |

수정 제안:

- 반별 목록에서는 이미 조회한 `submission.photos`와 읽기 상태·시각을 사용해 상태를 계산하거나, 실제 사진 ID를 일괄 조회해 전달한다.
- 완료 결과의 최신성 확인과 진행 상태 판정을 분리할 수 있다. 존재하지 않는 사진 ID를 만들어 함수에 넘기는 방식은 피한다.
- 실제 사진이 0장인 응시는 계속 ‘읽을 것 없음’으로 처리한다.

회귀 검증: 첫 업로드 후 pending/running/failed/stuck 각각의 목록 표시를 검사한다. 마지막 사진 삭제 및 재업로드도 포함한다. 상태 함수 단독 테스트 외에 `StudentLine`에 실제로 전달하는 입력을 검증해야 한다.

## 이전 리뷰 네 항목의 반영 상태

이전 문서의 네 항목은 다음과 같이 코드에 반영되어 있다. 같은 내용을 미수정 문제로 반복하지 않는다.

- 사진 변경 무효화: DB 트리거, 결과 저장·재적용 시 사진 집합 검사, 일괄 공개 RPC와 PDF 공개 시 답안 비교가 추가됐다. 다만 위 1번의 개별 폼 저장 경로는 남아 있다.
- OCR 시간 예산: SDK `maxRetries: 0`, 절대 deadline 기준 재시도, AbortController가 추가됐다. 로컬 모킹 서버 테스트가 통과했다.
- 폴링 조기 종료: 감시 시간이 stuck 기준보다 길어졌고, 종료 시 refresh와 미저장 입력 안내가 추가됐다. 순수 시간 계산 테스트는 통과했으며 실제 React 훅·브라우저 검증은 미실행이다.
- 크론 대상 누락: failed/stuck 조회 모두 DB에서 `runs < maxRetryRuns`를 LIMIT 전에 적용한다. 전용 DB용 회귀 테스트도 추가되어 있으나 이번에는 실행하지 않았다.
