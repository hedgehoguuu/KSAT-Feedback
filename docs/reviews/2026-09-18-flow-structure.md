# 전체 흐름·내용·코드 구조 리뷰

검토일: 2026-09-18. 기준 커밋: `ea7b6d6` 및 현재 작업 트리.

앱 소스는 변경하지 않았다. 기존 리뷰 문서와 `docs/runbook.html`도 보존했다. 아래에는 실제 오류 경로와 제품·구조 개선 제안을 구분해서 적었다.

**가장 먼저 할 일은 상태 변경 규칙을 일관되게 만드는 것이다.** 화면 → 서버 액션/API → 서비스 → DB 함수라는 기본 구조는 갖춰져 있다. 점수 계산, OCR 결과 정규화, 서버 전용 모듈, 공통 설정도 분리되어 있다. 다만 사진·정답·신청 상태가 바뀔 때 관련 데이터의 유효성을 검사하는 위치가 달라서, 화면에서는 성공했는데 실제 결과는 어긋나는 경로가 남아 있다.

## 1. 우선 수정할 문제

P1은 잘못된 성적·접수·반 정보가 저장되는 문제, P2는 조건에 따라 처리 누락이나 상태 불일치가 생기는 문제다. DB 관련 항목은 코드 경로를 확인한 결과이며, 실제 DB에서 재현한 것으로 해석하면 안 된다.

### 1) [P1] 정답표 수정 후 오래된 채점 화면을 저장하면 재채점 결과가 되돌아간다

위치: [0016_lms_photo_grading.sql:534](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/supabase/migrations/0016_lms_photo_grading.sql#L534), [course-actions.ts:254](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/lms/course-actions.ts#L254).

`save_answer_key`가 `lms_answers.correct`를 갱신해도 튜터 채점 또는 공개된 응시의 `updated_at`은 갱신하지 않는다. 따라서 기존 화면의 `rev`가 유효한 것으로 인정된다. 서버 액션은 최신 정답보다 폼의 O/X를 우선해서 저장한다.

- 발생 순서: 학생 답 1 / 정답 1 / O인 폼을 열어 둠 → 다른 탭에서 정답을 2로 수정해 DB는 X → 기존 폼 저장 → O로 복원.
- 수정: 정답표 버전과 채점 버전을 저장·공개 RPC에서 함께 비교한다. 최소 수정은 영향받는 응시의 버전을 같은 트랜잭션에서 갱신하는 것이다. 아직 답안이 없는 응시도 이전 정답표를 보고 입력 중일 수 있으므로 회차 단위 정답표 버전이 더 명확하다.
- 검증: 튜터 채점·공개된 응시·아직 답안 없는 응시 각각에서, 정답 변경 전 폼의 저장과 공개가 거절되는지 확인한다.

### 2) [P1] 오래된 초안은 사진이 삭제된 뒤에도 정상 접수할 수 있다

위치: [storage.ts:158](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/worker/storage.ts#L158), [store.ts:267](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/store.ts#L267), [submit/route.ts:122](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/api/submit/route.ts#L122).

크론은 접수에 연결되지 않은 사진을 24시간이 지나면 삭제한다. 브라우저는 저장된 `done` 상태를 만료 검사 없이 복원하고, 제출 API는 파일 경로 형식만 검사한다.

- 발생 순서: 업로드 후 접수 중단 → 24시간이 지난 뒤 정리 크론 실행 → 이어하기 → 제출 성공·접수번호 발급 → 워커에서 사진 다운로드 실패.
- 수정: 서버에 초안의 유효기간과 업로드 상태를 두고, 이어하기와 최종 제출에서 파일 유효성을 확인한다. 정리 작업과 제출이 충돌하지 않도록 초안을 제출 상태로 전환하는 규칙도 공유해야 한다. 누락된 사진만 다시 고르게 하고 고민·이메일은 보존한다.
- 검증: 정리 전·후 이어하기, 제출과 정리의 동시 실행, 일부 사진만 누락된 경우를 검사한다.

### 3) [P1] ‘새 반 만들기’가 기존 반을 덮어쓸 수 있다

위치: [classes.ts:241](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/classes.ts#L241), [admin/actions.ts:76](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/admin/actions.ts#L76).

새 반 생성과 편집이 모두 slug 기준 `upsert`를 사용한다. 생성 화면에서 기존 slug를 입력하면 기존 반의 시간·가격·제목·모집 상태가 바뀌고 기존 신청자 연결은 남는다. 폼의 `mode`는 돌아갈 주소를 정하는 데만 사용된다.

- 수정: 생성은 `insert`, 편집은 기존 ID를 대상으로 `update`한다. 중복 slug는 ‘이미 쓰는 주소’로 알려 주고 입력값을 보존한다.
- 검증: 이미 신청자가 있는 반의 slug로 신규 생성해도 기존 반과 신청자가 변경되지 않아야 한다.

### 4) [P2] 비밀번호 변경·초기화가 기존 로그인 세션을 무효화하지 않는다

위치: [auth.ts:56](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/lms/auth.ts#L56), [auth.ts:121](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/lms/auth.ts#L121), [users.ts:193](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/lms/users.ts#L193).

쿠키는 사용자 ID·만료 시각만 서명하며, 비밀번호 변경은 해시와 `must_change_password`만 갱신한다. 다른 기기에서 발급된 쿠키는 기존 만료 시각까지 유효하다(설정상 최대 30일). 초기화 직후에는 페이지 이동이 비밀번호 변경 화면으로 제한되지만, `assertRole`은 강제 변경 여부를 검사하지 않아 기존 세션의 쓰기 요청은 통과한다. 본인이 새 비밀번호를 설정하면 기존 세션의 페이지 접근도 다시 가능하다.

- 수정: `session_version`을 DB와 서명 쿠키에서 비교하고, 비밀번호 변경·초기화 시 증가시킨다. 본인 변경 완료 후에는 현재 브라우저에만 새 세션을 발급한다. 일반 쓰기용 권한 검사와 비밀번호 변경에 필요한 제한된 인증 검사도 분리한다.
- 검증: 서로 다른 두 세션 중 하나에서 변경하면 다른 세션이 거절되어야 한다. 초기화 직후 기존 쿠키의 쓰기도 거절되어야 한다.
- 이번 확인: 실제 `currentUser`, `changeOwnPassword`, `resetPassword`, `assertRole`을 모의 쿠키·모의 DB 응답과 연결했다. 동일 쿠키가 본인 변경 후 인증되고 초기화 후 `assertRole('student')`도 통과함을 확인했다. 외부 요청은 하지 않았다.

### 5) [P2] PDF 링크 발급 실패가 워커에서 완료 처리된다

위치: [process.ts:173](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/worker/process.ts#L173), [process.ts:276](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/worker/process.ts#L276).

`createSignedUrl()`의 오류를 확인하지 않는다. URL이 없으면 Notion의 PDF 링크 갱신을 건너뛰고, 다른 실패가 없으면 `synced`로 확정한다. 튜터가 사용할 링크가 없는 접수가 자동 재처리 대상에서 빠질 수 있다.

- 수정: 서명 URL 발급을 명시적인 처리 단계로 두고, 오류 또는 빈 URL이면 실패 기록과 재시도 대상으로 남긴다. PDF 생성뿐 아니라 링크 전달까지 성공 조건에 포함한다.
- 검증: PDF 업로드 성공 → 서명 URL만 503 → 완료 처리 금지 → 재시도 성공 후 링크 반영.
- 이번 확인: 실제 `processSubmission()`의 외부 통신을 모킹하고 서명 URL 요청만 503으로 만들었다. `failures: []`, `status: 'synced'`, `notion_ok: true`가 기록되는 것을 확인했다.

### 6) [P2] 한 번의 크론에서 같은 실패 접수의 재시도 횟수를 모두 쓸 수 있다

위치: [process.ts:320](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/worker/process.ts#L320), [0002_worker.sql:43](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/supabase/migrations/0002_worker.sql#L43).

배치가 매 반복마다 가장 오래된 `failed` 접수를 다시 가져온다. 실패 후 대기시간이 없으므로 빠르게 실패하는 같은 접수가 한 실행 안에서 연속 선택되어 5회 상한에 도달할 수 있다. 외부 서비스가 복구되어도 해당 접수는 자동 처리되지 않는다.

- 수정: `next_retry_at`과 오류별 재시도 간격을 두고, 한 배치에서 같은 접수를 중복 처리하지 않게 한다. 영구 실패와 일시 실패도 구분한다.
- 검증: 실패 접수 A와 신규 접수 B를 넣어, A가 한 배치에서 한 번만 시도되고 B도 처리되는지 확인한다.

### 7) [P2] 취소 신청을 복원하면 정원을 초과할 수 있다

위치: [classes.ts:486](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/classes.ts#L486).

신규 신청은 DB에서 반을 잠그고 정원을 검사하지만 관리자 상태 변경은 조건 없는 UPDATE다. 정원 3명인 반에서 A를 취소하고 D를 받은 뒤 A를 ‘입금 완료’로 바꾸면 활성 신청이 4개가 된다.

- 수정: 취소→활성 전환도 신규 신청과 동일한 반 잠금 아래 잔여 정원·중복 연락처를 확인하는 RPC로 처리한다. 인원을 더 받으려면 정원을 먼저 명시적으로 수정하게 한다.
- 검증: 마지막 자리를 신규 신청과 취소 복원이 동시에 요청해도 한 요청만 성공해야 한다.

### 8) [P2] 사진 묶음 선택 중 상한과 ‘업로드 중’ 판정이 실제 작업량을 놓친다

위치: [UploadSection.tsx:65](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/components/UploadSection.tsx#L65), [upload/page.tsx:35](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/apply/upload/page.tsx#L35).

선택한 파일을 한 장씩 변환한 뒤 store에 추가한다. 변환 대기 중인 나머지 사진은 장수 계산과 `busy`에 포함되지 않는다. 12장 선택 후 첫 장을 처리하는 동안 다시 11장을 선택하면 각 작업이 시작 시점의 잔여 장수 검사를 통과해 합계 상한을 넘을 수 있다. 이미 완료된 사진이 있으면 다음 사진을 변환하는 동안 다음 단계 버튼도 활성화될 수 있다.

- 수정: 선택한 전체 묶음의 자리를 한 번에 예약하고 변환 전부터 `queued` 상태로 등록한다. 추가 선택은 예약분을 포함해 계산하고, 과목 제거·시험 변경·제출 완료 시 남은 작업을 취소한다.
- 검증: 연속 파일 선택, 느린 이미지 변환, 처리 도중 과목 제거와 단계 이동을 브라우저에서 검사한다.

### 9) [P2] 이미 공개된 점수를 담은 PDF는 발송 중 채점 변경을 검사하지 않는다

위치: [feedback.ts:396](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/lms/feedback.ts#L396), [0016_lms_photo_grading.sql:665](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/supabase/migrations/0016_lms_photo_grading.sql#L665).

답안 비교가 ‘이번 발송에서 점수를 새로 공개하는가’인 `publish`에 묶여 있다. 이미 공개된 응시는 비교용 답안을 보내지 않으므로, PDF 생성·업로드 중 채점이 바뀌어도 이전 점수가 담긴 PDF를 발송할 수 있다.

- 수정: 공개 상태 전환과 PDF 내용 검증을 분리한다. 점수가 포함된 PDF는 공개 여부와 무관하게 채점·정답표 버전을 검사한다. 문항 정답·배점도 문서 내용이므로 검증 범위를 답안 O/X만으로 한정하지 않는다.
- 검증: 공개된 성적의 PDF 생성 중 점수를 바꾸면 발송 확정이 거절되어야 한다. 재발송도 포함한다.

### 10) [P2] 답변 발송 후 사진 잠금이 동시 요청에서는 지켜지지 않는다

위치: [student-actions.ts:69](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/lms/student-actions.ts#L69), [feedback.ts:125](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/lib/lms/feedback.ts#L125), [0016_lms_photo_grading.sql:104](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/supabase/migrations/0016_lms_photo_grading.sql#L104).

학생 액션은 시작할 때만 `feedback_ready_at`을 검사한다. 이후 Storage 작업을 기다리는 사이 튜터가 답변 발송을 확정해도 사진 추가·삭제가 계속 진행된다. 사진 변경 트리거가 응시를 잠그기는 하지만 발송 완료 여부는 검사하지 않는다.

- 수정: 사진 변경을 응시 잠금 안에서 발송 여부를 재검사하는 RPC로 묶는다. 삭제는 DB에서 변경을 승인하고 삭제할 경로를 작업 기록에 남긴 뒤 Storage를 정리한다. 현재처럼 파일부터 삭제하면 DB의 잠금 검사에서 거절될 때 원본 파일은 이미 사라질 수 있다.
- 검증: 학생 사진 요청을 사전 검사 직후 지연 → 튜터 발송 확정 → 학생 요청 재개 시 `LOCKED`와 원본 보존을 확인한다.

## 2. 전체 사용자 흐름과 내용

| 흐름 | 현재 동작 | 정리 제안 |
|---|---|---|
| 무료 접수 | 시험 → 과목·사진 → 고민 → 이메일·동의 → 접수번호 | 이어하기 유효기간을 실제 파일 수명과 맞추고, 제출 직전 누락 사진을 복구할 수 있게 한다. |
| 유료반 모집 | 수업 소개 → 반 선택 → 신청 → 운영자가 연락·입금 안내 | 완료 화면에 연락 예상 시간과 다음 행동을 명확히 적는다. 결제는 현재의 수동 운영을 유지해도 된다. |
| 수업 등록 | 운영자가 계정 생성·반 배정·접수번호 입력 | 신청자 화면에서 ‘계정 생성/기존 계정 연결/반 배정’을 이어 할 수 있게 한다. 자동 이름 매칭보다 운영자 확인이 적합하다. |
| 학생 LMS | 로그인·비밀번호 변경 → 시험 → 사진·질문 → 제출 → 결과/PDF | ‘사진 저장’, ‘질문 제출’, ‘채점 중’, ‘답변 도착’을 구분한다. 학생이 다음에 할 일 한 가지를 우선 표시한다. |
| 튜터 LMS | 반·시험 → 정답표 → OCR·채점 → 답변 → 공개·PDF 발송 | ‘사진 읽기 완료’, ‘채점 완료’, ‘점수 공개’, ‘PDF 생성’, ‘메일 전송’을 서로 다른 상태로 표현한다. |

**모집 내용과 실제 수업의 연결부터 결정해야 한다.** [class-copy.ts:27](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/config/class-copy.ts#L27)에는 80분 시험·언어와 매체·독서·문학이 있고, [접수 완료 화면](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/app/done/%5BreceiptNo%5D/page.tsx#L99)도 국어 3인 수업을 안내한다. LMS는 [수학·미적분](https://github.com/hedgehoguuu/KSAT-Feedback/blob/ea7b6d6/src/config/lms.ts#L31)이다. README에도 남은 작업으로 기록되어 있다.

- 수학으로 모집까지 전환하는 경우: 과목명, 시험 시간, 관찰 예시, 모의고사 기본값, 모집 메타데이터, 접수 완료 CTA를 함께 맞춘다. 숫자만 일괄 치환하면 180분 수업 구성과 상세 설명이 다시 어긋날 수 있다.
- 국어 모집과 수학 수업을 함께 운영하는 경우: 두 수업을 명시적으로 구분하고 반에 과목 정보를 둔다. 각 반이 어떤 LMS 과정으로 이어지는지 운영 화면에서 표시한다.

‘접수’와 ‘피드백 도착’도 시점을 구분하는 편이 좋다. 접수 완료 직후 `/class`로 이동할 수 있는데, 모집 첫 화면은 이미 피드백 문서를 받은 독자를 전제로 한다. 아직 못 받은 학생에게도 읽히도록 ‘무료 피드백 이후 이런 수업으로 이어집니다’라는 연결 문구를 두거나, 문서 발송 때 모집 링크를 중심적으로 안내할 수 있다.

운영 수치와 화면 문구는 같은 데이터에서 만들면 좋다. 현재 `CLASS.minutes`, `COPY.blocks`, 모집 페이지의 `80fr 10fr 90fr` 및 80분·90분 표기가 각각 존재한다. 수업 구성을 하나의 배열로 정의하고 합계·도표·문구를 파생하면 과목 전환 때 누락을 줄일 수 있다.

결제·환불·신청 속도 제한, 학부모 계정, 학생 제출 알림은 README에 범위 또는 운영 결정이 기록되어 있다. 이번 리뷰에서는 미구현 자체를 코드 오류로 분류하지 않았다.

## 3. 코드 구조를 정리하는 방향

폴더를 한꺼번에 옮기기보다 위 오류를 수정하는 단위로 책임을 나누는 편이 변경 위험이 작다. 기존 `config`, 순수 계산 함수, `server-only`, `must/rows/one`은 유지할 만하다.

| 현재 중심 파일 | 나눌 책임 | 효과 |
|---|---|---|
| `src/lib/lms/exams.ts` | 회차 관리 / 정답표 / 채점 저장 / 성적 조회·집계 | 점수 변경 규칙을 찾기 쉽고, 조회 변경이 저장 경로에 영향을 덜 준다. |
| `src/lib/lms/feedback.ts` | 시험지 사진 / 질문·답 / PDF 스냅샷 생성 / 발송 | Storage 작업과 학생 제출 잠금, PDF 발송 일관성을 각각 검증하기 쉽다. |
| `src/lib/classes.ts` | 공개 조회 / 관리자 반 변경 / 신청·정원 전이 | 생성과 수정, 신청과 복원의 다른 규칙이 함수 이름과 계약에 드러난다. |
| `src/components/UploadSection.tsx` | 업로드 대기열·취소 로직 / 화면 표시 | 파일 수·진행 상태·단계 이동 판정이 같은 대기열을 본다. |
| `src/lib/worker/process.ts` | PDF / 링크 / Notion / 메일의 단계별 결과와 재시도 | 오류 배열·플래그가 따로 움직여 성공을 잘못 판단하는 일을 줄인다. |

권장 의존 방향은 **화면 → 서버 액션/API → 서비스 → DB/Storage**다. 서버 액션은 인증·입력 해석·서비스 호출·화면 갱신에 집중하고, ‘가능한 상태 전환인가’와 ‘어떤 버전을 저장하는가’는 최종 DB 변경 지점에서 보장한다. 화면의 버튼 비활성화는 사용자 안내로 유지한다.

`updated_at` 하나를 모든 충돌 검사에 사용하는 대신, 먼저 정답표 버전과 채점 버전을 명확히 정의하는 것이 좋다. PDF는 생성에 사용한 버전을 기록하고 발송 확정 때 비교한다. 사진 변경·채점·발송이 함께 쓰는 응시 잠금 순서도 문서와 테스트에 한 번 정의한다.

예상 가능한 실패는 `STALE`, `LOCKED`, `FULL`, `UPLOAD_EXPIRED`처럼 타입으로 반환하고 화면에서 안내한다. 외부 서비스 장애·DB 오류는 별도 실패로 기록한다. 기존 LMS 결과 타입 패턴을 접수·모집 쪽에도 점진적으로 적용할 수 있다.

관리자 전용 개인정보 조회에는 조회 서비스 또는 각 페이지 진입점의 인증 검사도 두는 것이 좋다. 현재 `/admin`의 공통 레이아웃 검사에만 기대는 조회가 있다. 설치된 Next 인증 가이드는 레이아웃 단독 검사에 의존하지 말라고 안내한다. **이번 검토에서는 인증 우회를 실행 검증하지 않았으므로 확정된 유출 문제로 보고하지 않는다.**

## 4. 테스트·문서·배포 정리

기존 테스트는 점수·OCR·PDF의 핵심 계산을 잘 다룬다. 추가 검증은 정상 계산을 더 반복하기보다 경계에서의 변경에 집중하는 것이 좋다.

- 순수 로직: 업로드 전체 묶음 예약, 상태 전이 가능 여부, 버전 비교, 재시도 대상 선택.
- DB 통합: 정답 변경 후 오래된 폼 저장, 신규 신청과 취소 복원 충돌, 사진 변경과 발송 충돌. 실제 PostgreSQL의 두 연결을 사용하는 동시성 검증을 포함한다.
- 브라우저: 중단 후 이어하기, 연속 사진 선택, 비밀번호 초기화 전후 두 세션, 학생 제출부터 튜터 공개까지 한 회차.
- 외부 통신 모킹: 링크 발급만 실패, Notion만 실패, 메일만 실패, 각 단계 재시도. 이미 성공한 단계의 중복 부작용도 확인한다.

`test/logic.ts`와 `test/db.ts`는 점수·OCR·접수·신청·발송 시나리오별 파일로 나눌 수 있다. 테스트 수를 늘리는 것보다 어떤 사용자 흐름을 검증하는지 명시하는 것이 중요하다. DB 테스트는 데이터와 파일을 비우므로 전용 폐기 가능한 DB에서만 실행한다.

README는 실행 안내·현재 기능·상세 설계·과거 수정 이력이 한 파일에 모여 있다. README에는 빠른 실행과 문서 링크를 남기고, 운영 절차·구조·제품 결정·변경 이력을 각각 분리하면 찾기 쉽다. 기존 `docs/runbook.html`을 활용해 중복 운영 설명을 합칠 수 있다. 코드 주석에는 현재 규칙과 이유를 남기고 긴 과거 버그 서사는 결정 기록이나 커밋으로 옮긴다.

이미 배포된 마이그레이션의 동작을 바꿀 때는 기존 SQL 수정만으로 끝내지 않고 다음 번호의 마이그레이션을 추가한다. 그래야 기존 설치와 새 설치의 DB 함수 정의가 일치한다. 타입 검사·린트·순수 테스트를 CI 기본 검사로, 전용 DB 테스트를 별도 검사로 두는 구성이 적합하다.

## 5. 권장 작업 순서와 이번 검증

1. 정답표·채점 버전 검사, 초안·사진 수명, 신규 반 생성 덮어쓰기부터 수정한다.
2. 세션 무효화, 워커 실패·재시도, 취소 신청 복원, 업로드 대기열을 보강한다.
3. PDF 버전 검사와 사진 변경 잠금을 동시성 테스트와 함께 정리한다.
4. 모집 과목과 수업 구성을 맞추고, 신청→계정→수강 등록의 운영 동선을 연결한다.
5. 수정한 기능 경계에 맞춰 큰 파일과 테스트·문서를 분리한다.
